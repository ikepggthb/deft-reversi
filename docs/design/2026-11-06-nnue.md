# NNUE 評価関数の設計（2026-11-06）

> **結果**：7章の候補 B（パターン埋め込みネット、PEN）を実装した。同じ持ち時間で線形に +45 Elo、Edax 4.5.5 にレベル12で +88 Elo だった。[PEN の測定](../benchmarks/2026-11-06-pen/README.md)を参照。

`feature-new-engine` ブランチ（以下「旧版」）の NNUE を調べて、書き直し版（`feature/engine-v2`）に入れるときの設計をまとめた。

## 1. 目的

- レベル1（ほぼ評価関数だけ）でも Egaroucid に −17 Elo、レベル12 では −67 Elo だった（[engine-match](../benchmarks/2026-11-03-engine-match/README.md)）。中盤の悪手は MPC なしでも残るので、差の主な原因は評価関数と考えられる。
- 旧版の NNUE は、パターン評価よりも静的な誤差（MAE）が約1.1石小さかった。これを、**探索の速さを大きく落とさずに**取り込む。

## 2. 旧版の NNUE（調べたこと）

### 構造（v2）

| 部分 | 内容 |
|---|---|
| 入力 | 944,956 次元の疎な 0/1。1つの視点で最大255個が 1 |
| 入力の中身 | 石の位置 128（自分64・相手64）、合法手 128、象限の空き数 68、象限の偶奇 8、全体の偶奇 2、パターン 54個（v1 の42個 ＋ edge+2X ×4 ＋ corner2×5 ×8） |
| FT（最初の層） | 入力 × 256、重み int16。手番側と相手側の2つの視点で、それぞれ足し合わせる（accumulator、int32） |
| その後 | clamp(0, 4095) → 前半128 × 後半128 の積（pairwise）→ 2視点をつないで256 → 空き数で選ぶ8本の塔（256→32→32→1）＋ PSQT（入力ごとの線形項、8本） |
| 学習 | PyTorch、GPU（ROCm）。Huber δ=4、cosine LR、8通りの対称変換で増やす、100M 局面 × 8エポック。ラベルは最終石差 |

### 結果

| 評価関数 | valid MAE | 大きさ | 1回の評価 |
|---|---|---|---|
| パターン評価（旧 eval.json） | 5.63 | — | 約 0.12 µs |
| NNUE v2（回転で重みを共有しない、acc256） | 4.52 | 499 MB | 9.8 µs |
| **S2（回転で共有、acc128）** | **4.48** | 65 MB | 4.4 µs |
| S5（3^10 のパターンなし、acc128） | 4.63 | 17 MB | — |
| S6（3^10 のパターンなし、acc64） | 4.74 | 9 MB | — |

- 回転で重みを共有すると、小さくなり、しかも精度が上がった（v2 4.52 → S1 4.48）。
- accumulator は 256 → 128 では精度が落ちず、128 → 64 で落ちた（+0.12）。
- 既存のパターン評価の残りを学習する方式（残差）は、どれも悪かった。
- レベル5（深さ固定）の対局では、旧 eval.json に 67.8%、平均 +11.2 石。ただし**思考時間は44倍**だった。

### 気づいた点

1. **差分更新がない。** 評価のたびに、盤面から入力を作り直し、accumulator を全部足し直している（`state_from_board` → `with_accumulators`）。評価1回ごとに `Vec` も確保している。44倍遅いのは主にこのため。
2. **同じ時間での比較がない。** 強さの確認は、静的な MAE と深さ固定（レベル5）の対局だけである。評価が遅くなった分、同じ時間では浅くしか読めないので、深さ固定の勝率は強さを過大に見せる。
3. **量子化が SIMD に向かない。** accumulator が int32、活性が 0〜4095、密な層も int32 と i64 の丸めで計算している。pairwise と密な層はスカラーのままだった。
4. **特徴量の定義が2か所にある。** Python（学習）と Rust（エンジン）で別々に書き、fixture（28万行の JSON）で一致を確かめていた。どちらかを変えると壊れやすい。
5. **評価関数に依存する値のフィットが、学習ツールの外にある。** MPC は `tools/fit_mpc_nnue*.py` で別に合わせ、マッピングも手で決めていた。
6. **重みの形式が JSON**（514 MB）だった。
7. **探索からの呼び出しが trait object（`dyn`）。** 葉で毎回、仮想呼び出しになる。
8. 学習のスクリプトの MAE（4.479）と、エンジンでの MAE（4.495）が少し違う。量子化の誤差と考えられる。採否は、エンジンで測った値で決めるべきである。
9. 学習済みのモデル（`runs/small-S2-*` など）は、このマシンにはない。

## 3. 今の Deft で NNUE を入れるときの制約

### 探索がとても速い

- 中盤（レベル21、150局面）は 11.3億ノードを 51 秒で読む。**1ノードあたり約 45 ns** である。
- 今のパターン評価は、44個の表を引くだけ（i16 が 44個）で、差分更新もしている（`EvalState::played`）。
- 評価を呼ぶのは、主に葉（深さ0）である。深さ1のノードは、子を順に（β カットまで）評価する。このほか、深さ3以上での手の並べ替え、ProbCut の事前判定（静的評価から予想）、空き20以上の終盤の並べ替え（1手の探索）でも呼ぶ。

### 1手で変わる入力の数

ランダムな対局 300局で数えた（[今の 11パターン](../../deft-reversi-engine/src/evaluation/pattern/definition.rs)、4回転で44個）。

| 入力 | 1手で変わる数（1視点、平均） | 全部足し直すときの数 |
|---|---|---|
| パターン（44個） | 12.4個 → 引く・足すで **24.8 行** | 44 行 |
| 石の位置 | 置いた1 ＋ 返した 2.27 × 2 = **5.5 行** | 約30〜60 行 |
| 合法手 | **5.3 行** | 約20 行 |
| 象限・偶奇 | 6 行 | 9 行 |
| 計 | **約42 行**（2視点で約84 行） | 約110 行 |

- 1行は accumulator の幅ぶんの i16 である（128 なら 256 バイト）。差分更新でも、1手で約 21 KB の重みを読む。
- FT の表は約 65〜76 MB で、L3（このマシンは 12 MB）に入らない。今のパターン評価が読むのは、評価1回で 44 個の i16 だけである。
- このため、**差分更新をしても、評価1回は今の5〜10倍かかると見込む**（推定。最初に測る）。ノード数で見ると、同じ時間で読めるのは今の数分の1になる。
- 今の 11パターンで、64マスすべてを覆っている。石の位置の入力は、パターンと重なっているので、なくてもよいかもしれない（学習で確かめる）。

## 4. 設計

方針：**旧版の精度（S2）を土台にし、速さのための変更を加える。採るかどうかは、同じ時間での対局で決める。**

### 4.1 ネットワーク

| 部分 | 設計 | 旧版からの変更と理由 |
|---|---|---|
| パターン | 今のパターン評価と同じ 11パターン × 4回転。**回転で重みを共有** | S1・S2 の結果。差分更新で `EvalState` の 44個の番号をそのまま使える |
| 石の位置 | 学習で、あり・なしを比べる | パターンが全マスを覆うので、なくてよければ 1手あたり約5.5行減る |
| 合法手 | 128（自分・相手）。あり・なしと、「数だけ」を比べる | 数だけなら FT を通さず、密な層に直接入れられる（今の mobility 項と同じ考え） |
| 象限・偶奇 | 学習で比べる | 1手あたり6行 |
| FT | 幅 **128**、i16 | S2 で精度が落ちなかった。64 は落ちた |
| PSQT | 残す（空き数で8本） | 線形の部分を受け持つので、FT が狭くてよい |
| pairwise | 残す | 128 → 64 × 2視点 = 128 を密な層へ |
| 密な層 | 128 → 16 → 32 → 1。空き数で選ぶ（8本。16本も比べる） | 塔は小さいので、本数を増やしても速さはほぼ変わらない |

### 4.2 量子化と推論

Stockfish と同じ形にして、AVX2 で計算できるようにする。

- accumulator：**i16**（int32 にしない）。重みも i16。
- FT の出力：0〜127 に clamp。pairwise の積は右シフトして **u8** にする。
- 密な層：重み **i8**、積和は i32（AVX2 の `maddubs`）。出力を 0〜127 に clamp して次へ。
- 学習のときから、この丸めと clamp を入れて計算する（量子化を考えた学習）。
- 1回の評価で `Vec` を確保しない。決まった大きさの配列を使う。
- AVX2 がない CPU と WASM のために、スカラー版も持つ（結果は同じにする）。

### 4.3 差分更新と探索への組み込み

- **2つの色の accumulator**（黒の視点・白の視点）を持つ。手番が変わっても作り直さずに済む。
- **遅延更新**：手を打つときは「打った手と返した石」だけを積む。評価が必要になったときに、計算済みの一番近い祖先から足していく。
  - 深さ1のノードでは、親の accumulator を一度作り、子はそれぞれ「親 ＋ 差分」で評価する。
- accumulator（2 × 128 × i16 = 512 バイト）は、今の `EvalState` のように値で渡さない。スレッドごとの、深さで引くスタックに置く。YBWC の分割点では、手伝うスレッドに、その位置までの値を写す。
- パターンの番号は、今の `EvalState::played` のまま差分で求める。変わった番号（前と後で違うレーン）だけ、FT の行を引いて足す。
- 合法手の入力は、前の局面の合法手と XOR をとって、変わったマスだけ更新する。
- 子の重みの行は、手を打った時点で先読み（prefetch）しておく。
- 評価器は `dyn` にしない。探索を評価器の型で総称化する（`enum` でもよい）。パターン評価は、テスト・比べるための基準・Web 用に残す。
- **手の並べ替え**：まず NNUE で並べる。遅すぎれば、並べ替えと ProbCut の事前判定だけパターン評価を使う案も比べる（両方のモデルを読むことになる）。

### 4.4 モデルファイル

- 今の DPR2（パターン ＋ 調整した値）と同じ考えで、NNUE 用の形式を作る：見出し、構造の値（幅・塔の数・入力の種類）、重み、調整した値（MPC など）。
- 重みは i16・i8 のまま書く（JSON にしない）。読み込みは、メモリに読んでそのまま使える並びにする。
- 中身のハッシュを見出しに入れる。

### 4.5 学習

- **特徴量の定義は1か所（Rust）にする。** `deft-reversi-train` から、局面の束を入力の番号の束に変える関数を Python へ出す（PyO3）。学習は PyTorch で行う。旧版のような fixture での照合がいらなくなる。
- データは `egaroucid_rd_data_set`（約13.7億局面。再配布はしない）。空き数ごとに均等に取る（旧版で、偏りのバグがあった）。8通りの対称変換で増やす。
- 損失は Huber（δ=4）。ラベルは最終石差のまま。
- 採否は、**エンジンで量子化したモデルの MAE**（valid、空き数ごと）で決める。学習スクリプトの MAE は参考にとどめる。
- まず 100M × 8エポックで S2 相当を作り、旧版の 4.48 と比べる。そのあと、全データでの学習を試す（旧版では、8エポックでもまだ良くなっていた）。

### 4.6 評価関数に依存する値

学習ツールで全部フィットする（今のパターン評価と同じ）。

- 中盤の MPC（深さごとの a・b・σ）
- 終盤の MPC の式（偶奇で別の式、浅い探索の深さの表）
- ProbCut の事前判定の値（`predicted = slope · 静的評価 + intercept`）
- 必要なら、レベル表の確率と、終盤の並べ替えの閾値

評価関数が変わると σ も変わるので、同じ「98%」でも刈りの強さは変わる。フィットし直したあと、FFO 40〜59 の時間も測り直す。

### 4.7 Web

- FT が 65 MB では配れない。Web 用には、3^10 のパターンを外した小さいモデル（S5 相当、約17 MB、gzip で約7 MB）を別に作る。
- WASM の SIMD128 で、i16 の足し算と i8 の積和を書く。
- 今は Web がワークスペースから外れているので、ネイティブで採用が決まってから取りかかる。

## 5. 進め方と判定

速さの見込みが一番不確かなので、**学習の前に速さを測る**。

| 段階 | やること | 次へ進む条件 |
|---|---|---|
| 0. 速さの試作 | エンジンに推論・差分更新・SIMD を入れる。重みは乱数で十分（速さは重みによらない）。評価1回の時間と、レベル12・21 での中盤の速さを測る | 中盤の時間が今の何倍かを出す。目安は3倍以内 |
| 1. 学習 | 特徴量を Rust に寄せて、7章の候補（線形・PEN・小さい NNUE・S2 相当）を同じ学習器で学習する | MAE と評価1回の時間の、良い組み合わせを選ぶ |
| 2. フィット | 学習ツールで、MPC などを NNUE に合わせる | テストが通る。FFO 40〜59 の時間を記録する |
| 3. 強さ | (a) Deft どうし（NNUE 対 パターン）で、**同じ持ち時間**（`deft-gtp --game-ms`、1局ずつ）。(b) 同じレベルで Edax・Egaroucid（XOT、500局） | (a) で勝ち越せば採用 |
| 4. 仕上げ | ドキュメント、Release のモデル、Web 用の小さいモデル | — |

- 段階0 で遅すぎたら、FT の幅を64にする、石の位置の入力を外す、などの軽い構成を段階1で優先する。
- 時間を測るベンチマークは、1つずつ動かす。

## 6. 決めてほしいこと

1. **学習の環境**：このマシンには GPU がない（UHD 730、メモリ 8 GB）。旧版の学習は GPU で行っていた。265K の PC の GPU を使えるか、CPU で学習するか（100M × 8エポックは、CPU だと数時間〜1日程度と見込む。推定）。
2. **旧版の学習済みモデル**（`runs/small-S2-*` のチェックポイント）は残っているか。あれば、段階1 の前に、精度と速さを実物で確かめられる。
3. **パターンの組**：今の 11パターン（差分更新をそのまま使える）でよいか、旧版の 54個（corner2×5 などを含む）も比べるか。

## 7. モデルの見直し：S2 より良い候補

### わかったこと

**今のパターン評価は、旧版のパターン評価よりかなり良い。** 学習の記録（[2026-10-31-pattern-lr0.3](../benchmarks/2026-10-31-pattern-lr0.3/metrics.jsonl)、valid の MAE）を、旧版の表と同じく石数ごとの平均で比べた。測った局面の組と計算の仕方（今のほうは学習器で計算した値）が少し違うので、目安である。

| 石数 | 今の Deft（パターン） | 旧版 NNUE v2 | 旧版のパターン |
|---|---|---|---|
| 12 | 6.35 | 6.13 | 6.44 |
| 24 | 6.15 | 5.58 | 6.28 |
| 32 | 5.75 | 4.88 | 5.79 |
| 40 | 4.90 | 3.95 | 5.13 |
| 48 | 4.80 | 4.09 | 5.09 |
| 56 | 4.59 | 3.99 | 4.92 |
| 平均（12〜60） | **5.40** | **4.72** | 5.63 |

- NNUE との差は、旧版で比べた 0.9 ではなく **約0.7石**。差が大きいのは石数32〜56（約0.9〜1.0石）で、探索が評価を呼ぶ所である。
- **NNUE の差がどこから来るかは、まだ分かっていない。** 旧版の NNUE は、次の4つが同時にパターン評価と違う。
  1. 非線形（パターンどうしの組み合わせ）
  2. 合法手の位置の入力（パターン評価は、合法手の数の差だけ）
  3. 学習の仕方（Adam、8通りの対称変換で増やす）
  4. パターンの数（54個。corner2×5 などを含む）
- 2〜4 は、線形のままでも取り込める。

**Egaroucid 7.8.1 の評価関数は線形のパターン評価である**（`src/engine/evaluate_simd.hpp`）。
- 16パターン × 4 = 64個。ほとんどが10マスで、斜め＋X、cross、corner＋block など、Deft にない形がある。1段階あたり61万の重み、60段階。
- ほかに、手番側の石数の表がある。合法手の項はない。
- それでも、レベル1 では Deft より強い（Deft から見て −17 Elo）。線形の評価には、まだ伸びる余地がある。

**今のパターン評価が速い理由**：1段階の表が約600 KB で、L2 に収まる。読むのは i16 を44個だけである。NNUE の FT（約70 MB、全段階で共通）は、L2 にも L3 にも入らない。

### 候補

| 候補 | 中身 | 読むメモリ（評価1回） | 見込みの速さ（今と比べて） |
|---|---|---|---|
| A. 線形の改善 | Egaroucid 型のパターンを足す。鏡映で重みを共有するか、8通りの対称変換で増やす。合法手の位置の線形項を足す | 64〜70個の i16 | 約1.5倍 |
| **B. パターン埋め込みネット（PEN）** | 下で説明 | 44個 × 8バイト ＋ 小さい MLP | 約1.5〜2.5倍（推定） |
| C. 小さい NNUE | FT の幅を32〜64 にし、差分更新する | 1手で約84行 × 64〜128バイト | 約3〜5倍（推定） |
| D. S2 相当 | 4章の設計 | 1手で約84行 × 256バイト | 約5〜10倍（推定） |

**B. パターン埋め込みネット（PEN）**（新しい案）

- パターンの状態ごとに、1つの数（今）ではなく、**8個の i8（8バイト）**を持つ。1回の読み込みで、キャッシュラインは今と同じ1本である。
- パターンごとに4回転を足して、11 × 8 = 88 個にする。これに、合法手の数（自分・相手）、石数、偶奇を加える。
- 段階ごとの小さい MLP（88 → 32 → 1、重み i8）で評価する。積和は約3,000回で、AVX2 で約100命令である。
- 表は、1段階あたり約2.4 MB。段階を4石ごとにまとめれば、全体で約36 MB（今と同じくらい）になる。
- 差分更新は、今の `EvalState`（44個の番号）をそのまま使う。accumulator のスタックはいらない。
- **NNUE との違い**：NNUE は、全パターンを128次元に混ぜてから非線形にする。PEN は、パターンごとに8次元に縮めてから、MLP で組み合わせる。表現力は NNUE より小さいが、読むメモリは約1/40 である。
- 今の線形評価は、PEN で8次元を1次元にし、MLP をただの足し算にしたものにあたる。

### どの候補にも効く、学習の改善

- **ラベル**：今は最終石差だけを使っている。これには、その後の両者の悪手による雑音が入る。
  - 空き20以下の局面は、完全読みの値に置き換える（1局面あたりの時間は、最初に測って、使う局面の数を決める）。
  - それより前の局面は、浅い探索の値と最終石差を混ぜる。混ぜる割合は、学習で比べる。
  - 誤差の測り方も、完全読みの値を正解にした組を別に作る（最終石差の雑音の分だけ、誤差を大きく見積もらないため）。
- **対称性**：鏡映でも重みを共有するか、8通りの対称変換で増やす。旧版では、回転の共有で精度が上がった。
- **比べ方をそろえる**：全部の候補を同じ学習器（PyTorch）で学習し、同じ物差しで比べる。物差しは、エンジンでの MAE（空き数ごと）と、評価1回の時間である。

### おすすめの進め方

1. **速さを先に測る。** A〜D を乱数の重みでエンジンに入れ、評価1回の時間と、中盤探索の時間を測る（学習なしで、このマシンでできる）。
2. **差の出どころを切り分ける。** 同じ学習器・同じデータ（100M × 8エポック）で次を学習し、MAE を比べる。
   - 線形（今と同じ）
   - 線形 ＋ 合法手の位置
   - 線形 ＋ Egaroucid 型のパターン
   - PEN（8次元。4次元・16次元も）
   - NNUE（幅64・128）
3. MAE と速さの組み合わせが良い2〜3個を、Deft どうしの同じ持ち時間の対局で比べて決める。
4. 決めたモデルで、ラベルの改善（完全読み・探索値を混ぜる）を試す。

- 線形の改善や PEN で NNUE の差の大部分が取れれば、速さを落とさずに評価がよくなる。
- 取れなければ、そこで C・D に進む。
