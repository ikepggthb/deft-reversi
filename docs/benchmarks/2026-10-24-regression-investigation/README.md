# 復元後の終盤探索が遅くなった原因の調査

## 結論

前回の修正版からの退行は、主にFFO 49の探索量増加による。復元前リライトは元実装と異なるルート制御を使い、MPC確認探索も通常探索を流用してTTに記録していた。元の方式へ戻した際に、この情報蓄積と探索順が変わった。

切替実験では、MPC確認からTTへの書込みを復元すると後続の完全読みのノード数が減り、同じ確認探索で書込みだけを止めると現行と同じ完全読みノード数へ戻った。確認探索の処理時間そのものより、そこで残る着手情報が後続の手順付けに効いていたことを裏づける。

PV復元、アスピレーション窓の幅、安定化反復、通常窓MPCの有無を単独で変えても、この大きな増加は解消しなかった。

## 比較対象を区別する

- 元実装: `../deft-reversi-feature` f4192a0。
- 復元前リライト: `../2026-10-24-ffo40-49/` の新版列。40〜49合計11.653219秒。
- 復元後リライト（現在の本体）: `../2026-10-24-model-root-tt/` の新版列。合計12.880500秒。
- 下表は `/tmp` にコピーした診断版の相対比較で、本体のベンチマーク時間とは別。診断コード・実行ファイルの配置が異なるため、表の時間を以前の本体の秒数へ直接足し引きしない。

復元前後の合計増加は約1.227秒。FFO 49単体は3.316435秒から4.644553秒へ約1.328秒増加しており、ほかの局面の改善が一部を相殺している。元実装との約2.8%の差は別の比較で、FFO 48の差が大きい。

## FFO 49の切替実験

同じ復元後ソースのコピー、同じモデル・MPC係数・選択率、レベル60、1スレッド、CPU 1、native release。局面ごとに新プロセス・新Engineを使い、5回、実行順を周ごとに逆転した。全ケースで完全読みのスコア16と完了を確認。計時中にビルドを行っていない。トレース出力も無効にした。

| 診断用変更 | 時間中央値 | 探索ノード数 |
|---|---:|---:|
| 現行相当の診断版 | 4.781963秒 | 280,670,334 |
| 復元前リライトのルート制御群 | 4.001287秒 | 243,767,977 |
| 復元前リライトのMPC確認（TTあり） | 4.205336秒 | 223,502,785 |
| 同じ確認探索でTT書込みだけ無効 | 4.927799秒 | 279,196,213 |
| ルート＋TT付き確認の両方 | 3.361564秒 | 179,633,269 |
| 復元前リライトのフロー全体を再現 | 3.372143秒 | 192,348,817 |

各変更には相互作用があるため、減ったノード数を足し算して寄与率とは扱わない。「旧ルート」はルートでの手順付け・TT/MPC利用・窓の制御を含む群の差替えで、並べ替えだけの単独実験ではない。

### MPC確認探索が残す情報

本体では `search/tree.rs::probcut` がTTなしの `ordering_search` を呼ぶ。これは元実装の `nws_eval_leaf_no_mpc` に合わせた処理。一方、復元前リライトはMPCを無効にした `Context::node` を確認に使い、主表へ結果と候補手を記録していた。

完全読みのTTカットは深さ・方式・選択率が一致する境界だけを使う。浅い確認探索から残る候補手や表への登録情報は、方式が異なっても手順付けで使える。診断ではこの情報が探索順と探索量を変えていた。

段階別の完全読みノード数:

| 確認探索 | 最終完全読みだけのノード数 |
|---|---:|
| 現行のTTなし確認 | 273,691,567 |
| 通常探索を使ったTT付き確認 | 215,323,947 |
| 同じ通常探索でTT書込みだけを禁止 | 273,691,567 |

書込み禁止時の完全読みノード数は現行と完全一致した。モデル、選択率、最終深さを弱めて速くした実験ではない。生トレースは `confirmation-profiles.json` と各 `*-trace.log`。

### 復元前フローの再現

ルート、確認探索、通常窓MPCとTTの利用範囲を復元前リライトに合わせる診断も行った。FFO 40〜49の全10局面で、追加のPV検証ノードを差し引いた探索ノード数が、保存済み復元前バイナリの測定値と完全一致した。

FFO 49では、診断192,348,817ノード−追加PV検証6,031ノード＝復元前192,342,786ノード。ほか9局面も `previous-flow-reproduction.json` に照合結果を保存した。モデル読込や計測条件の変更を主因とする説明ではなく、探索処理の差で復元前の探索量を再現できた。

## 棄却した主因候補

初期診断では、FFO 49の最終完全読みが `[12,16]` と `[16,20]` の2窓に約2.28秒・約2.20秒を使っていた。これだけでは再探索の無駄が主因とは言えないため、窓を広げた実験を行った。

最初の独立した5回測定シリーズ（`ab-ffo49.*`）:

| 変更 | 探索ノード数 |
|---|---:|
| 対照 | 280,670,334 |
| PV復元を省略 | 280,647,984 |
| 安定化反復を省略 | 280,658,901 |
| MPCをゼロ窓だけに制限 | 280,462,211 |
| 完全読みの初期窓幅を4へ | 280,545,074 |
| 完全読みの初期窓幅を8へ | 280,619,109 |

広い窓では1回の探索に必要な仕事も増え、合計ノード数はほとんど変わらなかった。FFO 49のPV復元は別トレースで約0.00027秒・22,350ノード。40〜49のPV復元合計も約0.0092秒で、約1.227秒の増加の中心ではない。トレース時間は1回の診断値で、性能採用に使った5回中央値とは分ける。

PV表を省く、通常窓TTを以前の利用範囲へ戻す診断も、単独ではFFO 49の大きなノード増加を解消しなかった。初期スクリーニングは `screen-ffo49.json`。

## 元実装との差として確認した復元漏れ

前回「元へ戻した」と説明した内容には、まだ以下の差が残っていた。

1. **6空きの切替**: 元は5空き以下で単純なNegaAlphaへ切り替え、6空きではmobilityを使う簡易NWSを継続する。現在は6空きで単純なparity主体の処理へ降りている。
2. **同点時の手順**: 元の簡易NWSは同じ手順付け点なら先に列挙した手を選ぶ。現在の `max_by_key` は同点の最後を選ぶ。
3. **PV表の範囲**: 元はルートの空き数−4以上の局面にPV表を限定する。現在は通常窓の終盤探索全体で使っている。

FFO 48で一つずつ切り替えた探索量の診断（時間は各1回のため性能の採否には使わない）:

| 変更 | 探索ノード数 |
|---|---:|
| 現行相当 | 166,711,445 |
| 同点なら先の手を選ぶ | 162,555,942 |
| 6空きでもmobility手順を使う | 140,666,084 |
| 上の2つを併用 | 136,290,030 |
| PV表を元の範囲へ制限 | 166,711,445 |

6空きの切替の差は、FFO 48の探索量増加に関与している。元実装のFFO 48は140,619,730ノードだったが、新旧のノード定義や処理構成は完全には同じではないため、これだけで処理時間まで一致するとは扱わない。診断では探索量の減少に対して時間の減少は小さく、残る処理コストをこの実験だけで特定していない。PV表の範囲は復元漏れだが、今回のFFO 48のノード増加の主因とは確認できなかった。

この調査では本体に変更を適用していない。窓幅変更や、確認探索のTT利用をそのまま採用する判断もしていない。復元前リライトにあった独自の処理が特定局面で有利だったことと、元実装を正しく再現できていることは別に評価する必要がある。

## 再現と成果物

本体のソースハッシュが調査前と一致することを確認した。`baseline-source.tar.gz` は診断の基準にした復元後ソースのスナップショット、`diagnostic.patch` は診断用差分、`diagnostic.Cargo.lock` は依存関係、`variant-binaries.json` は実測に使った各バイナリのハッシュ。

```sh
python3 docs/benchmarks/2026-10-24-regression-investigation/reproduce.py --output /tmp/deft-regression-replay
```

このスクリプトは保存済みソースを `/tmp` へ展開して診断用にビルドする。本体の作業ファイルは変更しない。標準ではFFO 49の主要6条件を5周。`--case 48 --variants control,six_order,tail_first,tail_match,pv_root4` で追加診断も再現できる。展開・パッチ・ビルド・実行の再現確認として、control / FFO 40を1回実行し、本体と同じ8,728,417ノード・スコア38を確認した。

生データ: `ab-final-ffo49.tsv`、`ab-ffo49.tsv`、`stages.log`、`previous-all-trace.log`、`screen-extra-ffo48.json`。集計は対応するJSON。モデル・本体バイナリ・スナップショットのハッシュと実行条件は `environment.json`。
