# 持ち時間制：段階3-1 のデータ生成（通常の自己対局と延長モード、v3 と v4）

> develop/v2 には `tools/time-control/` を入れていない。ここに出てくるツールは `research/time-predict`（commit 9238780）または `ccr-a29b8244-tag4vo` にある。

時間管理の予測を精度よくする作業（[ロードマップ](../../design/2026-11-20-time-control-roadmap.md)）の段階3-1。段階4（感度分析）と段階5（モデル作成）で使う「反復ごとの時間」のデータを、時計のログ（`DEFT_CLOCK_LOG`）付きの自己対局で集めた。あわせて、評価関数 v3 と v4 で時間の予測に効く量が変わるかを比べた。

## 結論

- **時間切れは0件**。v4 で通常の対局1,000局と延長モード1,200手番、v3 で通常の対局960局（中断まで）。
- **v3 と v4 で、時間の予測に効く量は変わらない。** 中盤の倍率とノード速度は ±2〜3% の精度で同じ。25項目のうち23項目は、95%区間が「差なし」をまたぐ。またがなかった2項目（FlipSight の ENTRY +14%、4スレッドのノード速度 +2%）は、25項目を同時に見たときに偶然出る数と同じ程度で、ほかの条件で同じ向きの差がない。今回くらいの評価関数の変更（学習のやり直し、入力の変更）なら、時間の予測を作り直す必要はない。
- **延長モードの ENTRY は、打ち切りが多い。** 20秒・60秒・4スレッドでは、判断の後の ENTRY の約7割が延長の上限までに終わらなかった（20秒：終わったもの14、打ち切り39）。打ち切りを扱う回帰（Tobit）で使えるが、分布の右側を推定するには少ない。ENTRY を狙った追加の延長（延長を長く、空き数を絞る）を提案する（[残った課題](#残った課題)）。

## 条件

| 項目 | 内容 |
|---|---|
| 機械 | Intel Core Ultra 7 265K。P コア（CPU 0〜7）だけを使用。1スレッドは8局、4スレッドは2局を並行（`0-3;4-7`） |
| コミット | v3：`c9a3791`（`research/time-predict`）。v4：`f4aa62f`（`origin/develop/v2` をマージしたもの）。どちらもバイナリの写しで流した（v4 の写しの SHA-256 `0dc2cbcf…`） |
| モデル | v3：`model-v3-pen-mpc2`（SHA-256 `1a6e6b81…`）。v4：`local/data/v4b-run/mpc/model.dpr2` の写し（SHA-256 `cc444a8c…`） |
| 対局 | 同じバイナリ同士の自己対局。置換表 64 MiB。両者が時計のログを書く |
| 開局 | XOT（シード 20261120 でシャッフル、対称形を除く）。通常の対局は 200〜299 番、延長モードは 300〜449 番。どちらも調整用（1000番未満）で、最終評価の開局とは重ならない。各開局を両方の色で指す |
| 通常の対局 | GTP 2秒・20秒・60秒（1スレッド）、GTP 20秒（4スレッド）、FlipSight 6秒（1手の上限 1秒）。各200局 |
| 延長モード | GTP 2秒・20秒・60秒（1スレッド）、GTP 20秒（4スレッド）。各300局。片方（new）だけ `DEFT_CLOCK_EXTEND=E:S` で、E は開局と色から 20〜40 を一様に選ぶ。S は 2秒で 0.7、20秒で 5、60秒で 15 秒。延長した手番の直後で局を打ち切る（置換表と残り時間が変わり、その後の手番が実戦と違うため） |
| 時間 | v4：17:04〜21:41（4時間37分）。v3：20:32〜22:25（依頼者の指示で 4スレッドの 160局目で中断） |

コマンド：

```
DEFT_MODEL=local/time-control/stage3/bin/model-v4.dpr2 \
  tools/time-control/stage3.sh local/time-control/stage3/bin/deft-f4aa62f local/time-control/stage3/run-v4
tools/time-control/journal_table.py run-v4/n-*.tsv > n-v4.tsv     # run も同じ
tools/time-control/stage3_compare.py n-v3.tsv n-v4.tsv
```

`stage3.sh` は条件を順に流す。`touch OUT_DIR/STOP` で進行中の局のあとに止まり、同じコマンドで続きから再開する。生ログ（JSONL、v4 で 121 MB）は `local/time-control/stage3/` に置き、git には入れない。

| FlipSight 6秒 | 200局、時間切れ0、5.34 s | 200局、時間切れ0、5.37 s |
| GTP 20秒 | 200局、時間切れ0、18.2 s | 200局、時間切れ0、18.3 s |
| GTP 60秒 | 200局、時間切れ0、55.0 s | 200局、時間切れ0、54.9 s |
| GTP 20秒・4スレッド | 160局、時間切れ0、16.9 s | 200局、時間切れ0、17.0 s |
| 延長モード 4条件 | — | 各300局、すべて延長の直後で打ち切り。延長の前の時間切れ0 |

同じバイナリ同士なので、石差はどれもほぼ0。色を入れ替えた2局はほぼ同じ棋譜になる（60秒では、開局ごとの2局の平均が全部ちょうど0）。そのため、解析では**開局を単位**にして区間を出す（局の偶奇で分けた交差検証は使えない）。

各条件で、探索した手番は約10,000（v4）。約55〜62% が時計で止まり（TimeLimit）、残りは計画した反復をすべて終えた（Completed）。

## 残った課題

1. **延長モードの ENTRY が少ない。** 判断の後の ENTRY は条件ごとに 14〜38 件しか終わっていない。案：ENTRY を狙った追加の延長（20秒の対局、延長 30 s、空き 24〜32、約 30〜40 分）。
2. 同じバイナリ同士の対局は色を入れ替えてもほぼ同じ棋譜になるので、データの実質の量は局数の半分に近い。開局を単位に扱う。
3. 段階3-2（全手番の参照探索）は v4 で行う。規模は、時間の予測の当てはめ（次の作業）の結果を見て決める。
4. v3 の4スレッドは 160局で中断したまま。v3 と v4 の比較にしか使わないので、続きは流さない。
