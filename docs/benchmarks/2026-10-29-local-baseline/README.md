2026-10-29 ローカルPCでの基準値（1・2・4・8スレッド、deft・Edax・Egaroucid）

前回までの記録（[1スレッド1回目](../2026-10-28-engine-gap/README.md)、[2回目](../2026-10-28-edax-gap/README.md)、[並列の計測](../2026-10-28-multithread/README.md)、[並列の改善](../2026-10-29-multithread-splits/README.md)）はクラウドVMでの数値で、このPCとは比べない。全エンジンをこのPCでビルドし直し、基準値を取り直した。

## 環境

- Intel Core Ultra 7 265K（20コア、SMTなし）。Pコア＝CPU 0〜7（最大5.5 GHz、CPU 1・3は5.6 GHz）、Eコア＝CPU 8〜19（最大4.6 GHz）。L3 30 MiB、メモリ62 GiB。AVX-512なし。
- Linux 7.2.11-zen1、intel_pstate（powersave、ターボ有効）。デスクトップ（GUIセッションあり）。測定中にビルド・テストは走らせていない。
- CPU割当はPコアのみ：1スレッド＝CPU 4、2＝CPU 4〜5、4＝CPU 4〜7、8＝CPU 0〜7。8スレッドでは測定スクリプトやデスクトップの処理とCPUを共有する。
- 詳細（ハッシュ・ビルド方法）は `environment.json`。

## エンジン

- deft：`3b4e83d`（作業ブランチ `perf/local-baseline` の基点）。Rust 1.99.1、`RUSTFLAGS="-C target-cpu=native" cargo build --locked --release --example solve`。`exact N 256 --legacy-main-mpc`。
- モデル：`tools/convert_legacy_eval.py data/eval/eval.json` → `tools/convert_pattern_v2.py`。SHA-256 `3a07488c…a6069`（前回と一致）。
- Edax：`786421f`、`make build CC=gcc ARCH=native`（GCC 16.2.1）。`eval.dat` のSHA-256 `f8b22996…b792`（v4.4 `eval.7z` のものと一致）。`-n N -l 60 -h 23 -book-usage off`。
- Egaroucid：`2a65c87` ＋ `../2026-10-28-engine-gap/egaroucid-console-readlink.patch`。`g++ -std=c++20 -O3 -flto -march=native -pthread`（SIMD版のみ。このCPUにAVX-512がなく、Intelなので `-DHAS_AMD_PROCESSOR` なし）。`hash23.eghs` は `tools/bench/make_egar_hash.cpp` で生成しSHA-256 `0a44b764…d323` を確認。`-t N -l 60 -nobook -hash 23`。
- 主TTは全エンジン約839万項目（前回と同じ条件）。

## 方法

`compare_threads.py`（[前回](../2026-10-28-multithread/compare_threads.py)のものにCPU割当の指定 `--cpusets` を加え、Egaroucid SIMD版を対象にした）。各局面を新しいプロセス・空のTTで解き、周ごとにスレッド数の順を反転、局面ごとにエンジンの順を回転した。全実行でスコアを公開正解（`tools/bench/positions/ffo40-49-answers.obf`）と、空き数までの完全読みの完了を照合した（6周×4スレッド数×3エンジン×10局面＝720実行、不一致なし）。時間は各エンジンが報告する探索時間。

周回数：12周で開始したが、4周の時点で deft・Edax の10局面合計の周ごとの変動が±0.5%以内（前回のVMは±5%）だったため、6周で打ち切った（偶数周でスレッド数の実行順が均等になる）。7周目の途中の行は集計に使っていない（`summarize.py --rounds 6`）。打切りの際、未フラッシュだった標準出力の記録のうち最後の101実行分が失われた（`process-output.jsonl.gz` は619実行分）。スコア・深さの照合は各実行の直後に行っており、`results.tsv` の全行は照合済み。以後のためにスクリプトを1行ずつフラッシュするよう直した。

## 読み取り

- このPCでは1〜4スレッドで deft が3エンジン中最速。1スレッドの対Edax比0.851はVM（最後のホストで0.873）より差が大きいが、CPU・コンパイラが違うので比べない。
- 2スレッドの速度向上は deft 1.93倍、Edax 1.99倍。Edaxは2スレッドでノードが減る（0.971）。
- 8スレッドで deft の伸びが鈍る：速度向上5.45倍（Edax 5.79倍、Egaroucid 6.57倍）、ノード増加+15.1%（Edax +7.8%）。対Edax比が4スレッドの0.834から0.912に悪化し、Egaroucidとは同等になった。前回の課題「並列時のノード増加がEdaxより大きい」が、コア数の多いこのPCではより顕著に出ている。
- Egaroucidの8スレッドは周ごとの変動が大きく（1.724〜2.250秒）、ノード数も1スレッドより少ない。数え方が異なるため、エンジン間のノード比は優劣の根拠にしない。
- 局面別では、FFO46・47はスレッド数によらず deft が Edax・Egaroucid より遅い（1スレッドでの差がそのまま残る）。FFO41・42・44ではEgaroucidが最速。
- 8スレッドの測定はCPU 0〜7（周波数の高いCPU 1・3を含む）を使い、デスクトップの処理とも重なる。8スレッドの差を判断するときは周を増やすか、Eコアに測定以外の処理を寄せるなどの対策を検討する。

## 配布版・タグ版との比較（`runs/mt-release`、6周）

上の比較のEdax（`786421f`、v4.6から50コミット後で版表記は4.7）とEgaroucid（`2a65c87`、v7.8.3から21コミット後）は開発中のコミットだった。配布版で比べ直した。

- Edax 4.5.5：配布バイナリ `lEdax-x86-64-v3`（`~/Downloads/edax-4.5.5.zip`、AVX2版。v4版はAVX-512が必要でこのCPUでは動かない）。
- Edax 4.6：タグ `v4.6` を `make build CC=gcc ARCH=native` でビルド。
- Egaroucid 7.8.1：公式サイトのLinux向け配布物（`console_v7.8.1.zip`、ソース）を公式手順のg++版・clang++版の2通りでビルド（`-O2 -mtune=native -march=native`、g++は `-mfpmath=both`）。7.8.1にもreadlinkの未終端が残っていたため、同じ1行パッチを当てた。評価ファイルは前回と同じハッシュ、`hash23.eghs` もこのソースから生成して同じハッシュ。
- 評価ファイル `eval.dat` は全Edaxで同じ。その他の条件・CPU割当は上と同じ。全1200実行で正解・完全読みを照合した（不一致なし）。

読み取り：

- Edaxは4.5.5の配布バイナリが最速で、1スレッドでタグ4.6より27%、開発版 `786421f`（上の測定で11.728秒）より12%短い。前回までの比較相手（開発版Edax）は4.5.5より遅かったので、Edaxとの差は以前の記録ほど大きくない。1スレッドの対Edax 4.5.5は0.962。
- Egaroucidは公式手順のclang++ビルドが最速で、1スレッドではdeftと同等（deft/clang++ 1.004、全周でわずかにdeftが遅い）。g++ビルドより12%速い。前回の手順（g++ `-O3 -flto`、開発版）の11.976秒より、配布版clang++の9.930秒の方が速い。
- 2・4スレッドでは、deftは全相手より速い。
- 8スレッドでは、deftはEdax 4.5.5（1.016）、Egaroucid両ビルド（1.070・1.166）より遅い。deftのノード増加+15.3%は、Edax 4.5.5（+7.9%）の約2倍。
- 局面別では、FFO46・47でdeftは全相手より遅い。FFO41・42・44ではEgaroucidが速い。deftが大きく勝つのはFFO45・49。
- 今後の比較相手は、Edaxは4.5.5の配布バイナリ、Egaroucidは7.8.1のclang++ビルドとする。
