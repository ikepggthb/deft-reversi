## 2. 残りの作業

### 2.1 `Forecast` を `p.next` で場合分けする（`game_clock.rs`）

今は、次の反復の種類が分からないまま倍率を決めている。中盤は直近の比、終盤はすべて 1.6 倍。次のように分ける。

| `p.kind` → `p.next` | 予測の倍率 |
|---|---|
| どれでも → `None` | 予測しない（`false` を返す） |
| 中盤 d → 中盤 d′ | 今の比（1.5〜6 に収める）を `(d′−d)/2` 乗する |
| 中盤 → 終盤（最初のステージ） | 遷移の倍率（2.2 の測定で決める） |
| 終盤の選択的ステージ → 完全読み | 完全読みの倍率（同上） |
| 終盤の選択的ステージ → 次のステージ | 1.6（今のまま） |

`kind == Percent99` なら次は完全読みだと推測もできるが、24空きのように 95% を飛ばす計画もあるので、`next` で判断する。

### 2.2 遷移の倍率の測定（途中まで）

`ratio-partial-1thread.txt` に、1スレッド・TT 64 MiB・`timed_levels(60, 15s)` で、29局面分の反復ごとの完了時刻がある。v3 モデル、4論理CPUのクラウド環境で、3プロセスを同時に動かしたので少し遅めに出ている。各行は `種類:完了時刻(秒):評価値:最善手`。

ここまでの読み取り（1スレッド）：

- **中盤 → 85%**：最後の中盤反復にかかった時間の、多くは3〜5倍、最大10倍（20〜30空き）。32〜34空きでは、15秒以内に終盤ステージへ届かなかった。
- **99% → 完全読み**（20空きは 98% → 完全読み）：22〜24空きで2〜10倍、中央値は約4〜5倍。4スレッドで測ったとき（`docs/design/2026-11-18-time-management.md`）は、24空きで11倍、26空きで43倍だった。スレッド数で倍率が変わるので、ベンチマークで使うスレッド数で測り直すこと。
- 初期案：中盤 → 終盤は `max(3, 4·1.3^(空き−28))`、完全読みは `max(2, 5·1.5^(空き−23))`。少し多めに見積もっても、そのステージが次の手番に回るだけなので損は小さい。少なく見積もると、`hard` まで時間を捨てることになる。

測り直し：

```sh

DEFT_MODEL=model.dpr2 ./target/release/probe GAMES.txt 15 34,32,30,28,26,24,22,20 8 1 0 > ratio.txt
# 引数: 棋譜ファイル 制限秒 空き数リスト 局数 スレッド数 飛ばす局数
# 棋譜: deft-reversi-cli self-play -l 8 --random 8 --seed 11 -o GAMES.txt 24
```

## 3. レビューで指摘したほかの点（未対応）

`a21b8c9` のレビューで指摘し、2章に入っていないもの。

- **完全読みの時間見積もりにスレッド数が入っていない**：`2ms + 18ms × 2^(空き−17)` は1スレッドを前提にしているように見える。4スレッドでは約3倍、`target-cpu=native` ではさらに速くなるので、予約が大きすぎて中盤に回る時間が減る。`adapt`（実測 NPS で補正する案）は不採用にしたが、`threads^0.8` で割る固定の補正なら副作用は小さいはず。
- **予約時間を多めに数えている**：将来の手番すべてに完全読み1回分を予約しているが、一度完全読みすれば、それ以降の手番は置換表に答えが残っていてほぼ0秒になる。安全側なので実害は小さいが、時間が余る原因の一つ。
- **止めた理由が区別できない**：`Forecast` はストップハンドルで探索を止めるので `StopReason::Requested` が返り、Ctrl-C で止めたときと区別できない。ログや統計を取るときに紛らわしい。
- **不採用にした案の判定**：`phase` −0.31石、`front_mpc` −0.59石、`adapt` +0.06石はどれも誤差の範囲で、「今の配分が最適なバランス」とまでは言えない。試した案が多く、同じ調整用の開局で選んでいるので、たまたま良く見えた案を選ぶ偏りも入る。最終評価の開局を分けているのはよい。

## 4. 時間配分を最適化する考え方（提案）

「中盤を26手程度より深く読むより、その時間を終盤 MPC や完全読みに回した方が強いのでは」という見立てを、数値で決めるための方法。

### 4.1 原理

時間 t を使ったときの期待損失（最善手と比べて何石損するか）を、手番ごとに L(t) とする。総持ち時間 T の中で損失の合計を最小にすると、**全手番で −dL/dt（1秒あたりに減らせる損失）が等しくなる**配分が最適になる（ラグランジュ乗数の条件）。中盤を深く読み進めると −dL/dt が小さくなり、同じ時間で終盤 MPC の方が損失を多く減らせるなら、そちらへ回すべきだということになる。

### 4.2 損失の表を作る（オフライン）

1. 自己対局から、空き20〜50の局面を数百個集める。
2. 強い探索（完全読み、または深い MPC）で全合法手の値を出し、正解表を作る。
3. 各局面で、中盤 d = 10, 12, …, 30、終盤 MPC 85/95/98/99%、完全読みを走らせ、選んだ手・損失（正解での最善手の値 − 選んだ手の値）・時間を記録する。
4. 空き数ごとに「時間 → 期待損失」の曲線を作る。どの空き数で、どの深さから中盤より終盤 MPC の方が得になるかが分かる。

`feature/cli-v2` で 20空き・40局面について測った値（中盤12手 29.7ms・1.05石損、中盤16手 112.8ms・0.55石損、終盤85% 71.4ms・0.05石損）は、この表の一部にあたる。20空きでは、すでに終盤85% の方が中盤探索より効率がよい。

### 4.3 調整できる箇所

| 箇所 | 内容 |
|---|---|
| 中盤の深さの上限 D_max | `timed_levels` の中盤探索を D_max（例：26）で止める。余った時間は、その手で終盤 MPC が間に合えばそちらに使い、間に合わなければ時計に戻す |
| 終盤 MPC に入る空き数 | 今はレベル表に従っている。損失の曲線から、持ち時間ごとに決める |
| 手番ごとの重み w(e) | 今は均等。−dL/dt の大きい空き数帯（予想では24〜34空き）を重くする |
| 終盤用に残す時間 | `Budget` の予約の計算 |

### 4.4 調整のしかた

1. 4.2 の表を使い、一局分の配分に対する期待損失の合計を計算だけで評価する。D_max、w(e)、予約の係数をグリッド探索やベイズ最適化で調整し、持ち時間（10秒、60秒、5分）ごとに最適な値を出す。
2. 実機での対局は確認だけに使う（SPRT、数百局、調整に使っていない開局）。
3. その後、対局中に実際の完全読み時間から見積もりを補正する方法や、候補手が拮抗しているときだけ深く読む方法（Egaroucid）を試す。
