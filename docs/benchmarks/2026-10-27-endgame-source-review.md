2026-10-27 終盤探索のソース比較

このレビュー後にTT先行探索・局所TT照会再利用・実験用の11〜13マス評価を実装した。以下は変更前の調査記録であり、現在の実装と測定結果は[実装レポート](2026-10-27-endgame-implementation/README.md)を参照。

対象は現 deft の作業ツリー（refactor/engine-layout、基点 8ab1682）、Edax 786421f、Egaroucid 2a65c87。既存の未コミット修正を含めて確認した。本調査では探索実装を変更せず、追加測定もしていない。

ソースから確定できるのは「余分な処理がある」「探索順・再利用範囲が違う」ことまでである。各差が実時間差の何割を説明するか、代替実装が速いかは断定しない。特に選択探索と完全読み、評価モデル、探索ノードの数え方をそろえない NPS 比較では、原因を分離できない。

優先順位は、改善の確実性ではなく、終盤における呼び出し頻度・避けられる処理・変更範囲から判断した。

| 優先 | 差 | 主な範囲 | 影響の種類 |
|---|---|---|---|
| 1 | TT 候補探索前に全候補の手順付けを行う | 汎用探索、局所 NWS 7〜13 | カット前の処理費用 |
| 2 | 11〜13 の手順付け情報が少ない | NWS 11〜13 | ノード数増加の可能性 |
| 3 | 子の局所 TT 照会を再帰入口で繰り返す | NWS 7〜13 | 1 ノードの費用 |
| 4 | 5〜6 の探索で合法手の一括生成と個別 flip を併用 | NWS 5〜6 | Edax に対する処理量の差 |
| 5 | parity を局面ごとに再計算する | NWS 5〜13、last4 入口等 | 1 ノードの費用 |
| 6 | 6 マスにも局所 TT、得た候補手は探索に使わない | NWS 6 | TT 費用と再探索削減の釣り合い |
| 7 | 末端カーネルの構成と優先手が異なる | last1〜4、5〜6 | 命令数・ノード数の差の可能性 |
| 8 | スコアだけで済む NWS でも Line を扱う | 主に NWS 14 以上と準備探索 | 戻り値・PV 操作の費用 |
| 9 | 共有 TT が 1 コア時にも同期と再ハッシュを行う | 汎用探索・ETC | TT 操作の費用 |

1. TT 候補を先に探索する経路がない。

deft の tree.rs:185〜243 は各候補について ETC、評価または浅い探索、合法手数計算を済ませ、248 以降で初めて最善候補を探索する。TT 候補自身も ordering.rs の評価を通る。TT ボーナスはこの計算後に加算される。

したがって TT 候補だけでカットできる局面でも、他候補の評価費用を払う。例えば候補が 8 手あり、TT 候補の探索でカットできる場合にも、現実装は原則として 8 手分の手順付けを先に行う。ETC や wipeout 等でそれ以前に戻る経路は別である。

Egaroucid midsearch_nws.hpp:405〜419 は TT 候補を先に再帰探索し、失敗した場合だけ move_list_evaluate_nws を実行する。Edax move.c:313〜316 は TT 候補自身の通常の手順付け計算を省く。ただし、確認した Edax の経路を「他候補の評価より常に先に TT 候補を再帰探索する」と解釈してはいけない。

deft の局所探索も tail.rs:204〜254 で他の全候補の子 TT・合法手数を調べてから、255 以降で TT ボーナス付き候補を探索する。途中の mobility<=1 の子は即探索されるため、TT 候補より先になることもある。これは順序の設計上の事実であり、常に不利という意味ではない。

2. 11〜13 マスで手順付けに使う情報が少ない。

deft tail.rs:241 と tree.rs:524〜526 は、角を 2 倍に数える相手合法手数と四分割 parity の重みだけである。先に調べる子の局所 TT、低 mobility 即探索、保存済み候補手も併用するが、11〜13 専用の評価はない。

Egaroucid は search.hpp:27〜30 と endsearch_nws.hpp:295〜378 により、11〜13 は終盤用のパターン評価を追加し、7〜10 は parity と mobility を中心にする。終盤専用評価は evaluate_simd.hpp:546 にある。深い側の 1 回のカットで省ける子孫が多いことに合わせた構成である。

Edax move.c:319〜333 の fast ordering は升の種類、parity、potential mobility、corner stability、weighted mobility を組み合わせる。AVX2 経路では合法手と potential mobility をまとめて計算する。

deft は候補評価単体を軽くしている一方、相手合法手数が似た複数候補を識別する材料が少ない。探索ノードが増える有力な仮説である。ただし重み・モデルを移せば減るとは限らず、11〜13 に通常評価を追加するだけでは費用増になる可能性もある。

3. 子 TT 照会と再帰入口の照会が重複する。

deft tail.rs:213 の local_end_entry(child) の後、231 または 261 の再帰で endgame_score_entered に入り、107〜125 で同じ子の hash・比較を行う。最初の照会がヒットしてもカットしなかった場合、またはミスした場合にも繰り返す。候補評価と再帰の間に別の探索が入る場合は内容が変わり得るので、単純に常に同じ値を読むという意味ではない。

Egaroucid endsearch_nws.hpp:223〜279 は親が子の TT を照会・保存し、子の関数入口では自局面の TT 照会をしない。後段で保存先の hash を再計算する経路はあり、TT 関連計算がすべて 1 回というわけではない。

deft も親側に責務を集めるか、子に照会結果を渡せる。ただし quality、上下限の視点の反転、途中中断時に保存しない条件を維持する必要がある。候補すべての状態を大きくして保存する設計は避けたい。

4. 5〜6 マスの合法手生成方式が Edax と違う。

deft tail.rs:309 で盤面全体の合法手を生成し、327 で実際に探索する手の flip を計算する。合法手生成と個別反転計算は別処理である。

Edax endgame.c:425〜456 は保持している空きマス列を parity 順にたどり、NEIGHBOUR と board_get_move で合法性と反転を確認して直ちに探索する。早い手でカットすれば、残りの空きマスの合法性を調べずに済む。空きマス列自体の維持費用はある。

Egaroucid endsearch_nws.hpp:64 も全合法手を生成するので、この差は Egaroucid に対する理由には使えない。空きマスが少ない範囲だけ Edax 型を試す価値がある。

5. parity の差分状態を持たない。

deft tree.rs:466〜476 の odd_regions は毎回 4 領域の popcount を行う。tail.rs:200、320、last_four.rs:374 の final_parity 等で局面から再構築する。last4 の final_parity は空きマスを再走査する。

Edax は search.c:714、Egaroucid は search.hpp:387 等で着手した領域のビットを XOR して更新する。Egaroucid の last4 SIMD には別の孤立空き優先があり、全段階を同一の parity 更新方式とみなすべきではない。

deft も上位から小さい parity 値を渡せば再計算を減らせる。単独の差は小さくても出現頻度が高い。状態の引数追加やレジスタ圧迫との比較は必要である。

6. 6 マスの局所 TT は、参照実装より深い末端まで残っている。

deft tail.rs:84〜130 により 6 マスでも TT を照会・保存する。その後は ordered_endgame ではなく tail_score_impl を実行するため、TT に best があっても 6 マスの探索順には使わない。上下限によるカットは有効である。

Edax endgame.c:491 と settings.h:163、Egaroucid endsearch_nws.hpp:175 と search.hpp:27 は 6 マス以下を TT なしの浅い探索へ渡す。deft は hash、quality のロード、局面一致比較、保存を支払う代わりに、再訪時に探索を省いている。

6 マス TT をなくすと必ず速いとはいえない。以前の試行で「6 マスにも mobility 順序を付ける」は一貫した改善になっておらず、この TT の有無とは別の変更として扱うべきである。

7. 専用末端カーネルは既にあるが、Egaroucid の SIMD 専用経路とは構成が違う。

deft last_four.rs は専用 solve4→solve3→solve2→最終反転数へ降りる。通常の flip は AVX2、最終反転数は BMI2 が有効なビルドでは PEXT と表を使う。したがって「deft は末端も汎用探索だけ」「SIMD がない」は誤りである。

Egaroucid endsearch_nws_last_simd.hpp:173、240、321 は盤面を __m128i で渡す last2〜4 を持ち、同:105 の AVX2 last1 には最終反転数をすべて数えずにカットする経路もある。AVX512 専用経路と混同せず、実際のコンパイル条件で比較する必要がある。

また Egaroucid は endsearch_nws.hpp:83 と endsearch_nws_last_simd.hpp:335 で、8 近傍に他の空きがない孤立空きマスを優先する。deft の四分割 parity だけでは区別できない孤立性を使う。これもノード数の差の候補である。

deft の LeafSearch::visit は各訪問で中断処理のラッパーを通る。node_limit がなければ原子的な予算確保は実行されず、中断検査は基本 256 ノードごとなので、「毎ノード atomic increment が主因」とは言えない。厳密な node_limit の維持には特に注意が必要である。

8. スコアだけを必要とする上位 NWS に PV 用の Line が残る。

deft session.rs:78〜96 の Line は 128 個の Action 配列を持ち、leaf と prepend はその構築と PV のコピーを記述している。tree.rs の node と sibling はゼロ窓でもこれを返す。

Edax NWS_midgame/NWS_endgame、Egaroucid nega_alpha_ordering_nws/nega_alpha_end_nws は整数スコアを返す。deft も残り13 以下の局所 NWS は既に整数戻り値であり、この問題を末端全体に広げてはいけない。

主な改善対象は 14 以上、準備探索、汎用の選択探索である。コンパイラが一部を除去する可能性があるため、配列の大きさをそのまま毎回の実コピー量とみなすことはできない。NWS を score-only に分ける理由としては明確である。

9. 1 コア時にも共有 TT の同期コストが残る。

deft transposition.rs:51〜89 の読み取りは sequence と payload の複数 atomic load と検証、保存は CAS と publication を行う。store は 133〜173 でクラスタの読み直しも行う。cluster の hash は 116〜122 で毎回計算され、親 ETC と再帰入口、保存で共有されない。

Edax には hash_prefetch と thread-local 専用 get/store がある。Egaroucid にも共有 TT のロックはあるため、「他のエンジンは同期しない」という比較は誤りである。一方、deft には共有 TT の 1 コア専用バックエンドがなく、共有安全性のための操作を残す。

deft の共有 TT は 64 バイトに 2 エントリ、Edax の通常 Hash は局面16+データ8バイトで HASH_N_WAY=4。deft は sequence 分の領域を使う。置換候補の数と密度は違うが、同容量でのヒット率・衝突率や実時間が悪いとまではソースだけでは決められない。局所 TT の単純増量も以前の測定では改善していない。

追加で確認したが、主因として扱わない差もある。deft は main/PV の同条件の上下限を交差させず、幅が狭い片方を選ぶ（tree.rs:124〜136）。片方に有効な TT 候補がない場合のもう片方へのフォールバックも限定的である。ただし広い窓中心の問題で、7〜13 の局所 NWS の熱い部分には直接効かない。

現時点で優先する変更は、TT 候補の先行探索、11〜13 の専用手順付け、局所 TT 照会責務の整理。その次に 5〜6 の探索方式と parity 差分更新を個別に比較する。合法手・評価状態の一括再利用は前回の試作で中盤約4.2%悪化し、終盤も改善しなかったため、一般論だけで再採用すべきではない。

以上は遅さを説明し得る実装差のリストであり、各差が既存の実時間差を説明する比率を実証したものではない。モデルが異なる評価・MPC の強さも探索ノード数を変えるため、これらを除外してソース構造だけに全差を帰属させることはできない。
