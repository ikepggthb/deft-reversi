# リファクタリングの確認（2026-10-29）

探索の動作を変えないリファクタリング3件（`bb047f6`・`a3e4397`・この記録と同じコミットの `node()` 分割）について、結果と速度が変わらないことを確かめた。

## 結果の一致

各変更の後に、1スレッド・256 MiB TT・CPU 4 で FFO40〜49 を解き、変更前（`7ac9e71`、バイナリは `deft-a6d7846` と同一）と比べた。10局面すべてで、スコア・最善手・完了深さ・ノード数・葉の数・停止理由が一致した。

## 速度（`node()` の分割）

`compare_many_threads.py`、6周、周ごとに実行順を入れ替え、各局面は新しいプロセス、全実行で公開正解と一致。1スレッドは CPU 4、8スレッドは CPU 0〜7。

| 版 | 1スレッド | 8スレッド | 生データ |
|---|---|---|---|
| 分割したヘルパーが別関数になった版 | 1.0060（速い周 0/6） | 1.0056（2/6） | `runs/t1`、`runs/t8` |
| ヘルパーを `#[inline(always)]` にした版（採用） | 1.0012（2/6） | 0.9978（4/6） | `runs/inline-t1`、`runs/inline-t8` |

比は変更後÷変更前の中央値。最初の版は、`score_moves` と `search_siblings` が `node` から外れた別の関数になり、1スレッドで6周すべて遅かった。ノード数は同じなので、探索ではなく呼び出しの費用による。インライン化すると `node` は元のように1つの関数に戻り、差は周ごとのばらつきの範囲（±0.5%）に収まった。
