# Edax 4.5.6の測定条件・配布バイナリの確認

2026-11-16、FFO33〜51でEdaxが遅く見えるという指摘を受け、設定・計時・ビルド差を調べた。指定ミスや配布バイナリが明らかに遅いという原因は、確認した範囲では見つからなかった。

## 設定と計時

- 使用していたのは奥原版Edax 4.5.6の公式Linux x86-64-v3配布バイナリ。このCPUで使えるAVX2向けであり、32ビット版や汎用SSE2版ではない。i3-14100はAVX-512を持たないのでv4版は今回の比較には使っていない。
- 実行中の `options` コマンドで `n=8`、レベル60、hash bits 23、`book allowed: false`、評価データのパスを確認した。[確認結果](options.txt)。`search selectivity: -1` は手動上書きなしの意味で、レベル60の完全読みを使う。結果行の終局までの深さと正解石差も確認した。
- [公式v4.5.6のmain.c](https://github.com/okuhara/edax-reversi-AVX/blob/v4.5.6/src/main.c) は全引数を解析してからsolveを呼ぶ。したがって `-solve FILE` の後ろに指定した `-n 8` 等が無視される並び順ではない。
- 既存ツールは局面結果行の `分:秒` を読んでいる。CPU時間の総和やプロセス起動時間を探索時間と取り違えていない。入力・エンジンの順番・新規プロセスでのTT初期化も前回と同じ。

## 再測定とビルド比較

FFO33〜51、8スレッド、CPU 0-7、hash bits 23、定石なし。局面ごとに新規プロセスを起動し、ビルドの順番を局面・回ごとに回して各3回測定した。評価データは同一。ビルドは計測前に終え、ソースの探索ロジックは変更していない。Deft・Egaroucidはこの再測定には含めていない。

| Edax 4.5.6のビルド | 1回目 | 2回目 | 3回目 | 合計の中央値 |
|---|---:|---:|---:|---:|
| 公式配布版 x86-64-v3 | 7.368秒 | 7.692秒 | 7.654秒 | 7.654秒 |
| GCC 14.2・native・LTO | 8.103秒 | 8.111秒 | 7.960秒 | 8.103秒 |
| Clang 19.1.7・native・LTO | 7.634秒 | 7.825秒 | 7.781秒 | 7.781秒 |

前回の公式配布版は7.795秒。今回は7.368〜7.692秒、中央値7.654秒で、前回だけ極端に遅かったという結果ではない。今回試したGCC/ClangのCPU向け再ビルドは配布版より速くならなかった。コンパイラ設定・PGO等の全組合せを網羅した確認ではない。

TT容量の影響も切り分けるため、公式配布版を `-h 24` で追加1回測った。合計7.662秒で、`-h 23` の中央値7.654秒から大幅には変わらなかった。Edaxのソース上では主表とPV・浅い探索用の表があり、24-byteエントリで主な共有TTは `-h 23` が約216 MiB、`-h 24` が約432 MiB（ほかにロック・局所表等がある）。Deftの256 MiBとバイト単位で一致させたものではない。

## 前回の時間差の見方

[前回の同条件の測定](../2026-11-16-ffo33-51-console-8thread/README.md)の報告値：

| | 合計秒 | ノード数 | ノード数÷時間 |
|---|---:|---:|---:|
| Deft CLI | 6.589 | 1,086,188,562 | 約1.65億/秒 |
| Edax 4.5.6 | 7.795 | 2,435,896,088 | 約3.12億/秒 |

各エンジンの報告ノード数では、EdaxはDeftの約2.24倍を探索している。ノード数を時間で割った値はEdaxのほうが高い。したがって単純に「Edaxの1ノードの処理が遅い」という結果ではなく、探索量の差が総時間に関係していると考えられる。ただしエンジン間でノードの数え方は完全に同一とは限らず、この比だけで内部実装の効率を断定しない。

結論は、このCPU・FFO33〜51・指定されたモデルとTT設定でEdaxの所要時間は再現し、今回調べた実行設定やビルド差では大幅な高速化は見つからなかった、という範囲。Deftが一般にEdaxより強い、あるいはすべての局面で速いという意味にはしない。
