# 空きの多い完全読みが遅い原因の調査（2026-11-03）

[FFO 40〜59 の比較](../2026-11-03-ffo-engines/README.md)では、空き28〜30の問題が Edax・Egaroucid より遅かった。

- 57・58（空き30）：Edax・Egaroucid の 1.3〜1.6倍
- 53・54（空き28）：Egaroucid より 8〜13% 遅い

その原因を調べた。条件は前回と同じで、1スレッド、CPU 2 に固定、TT は 256 MiB、モデルは `mpc-formula/model.dpr2` である。

## わかったこと

1. **空き25以上の MPC の傾き・切片は、主な原因ではない。**
   - 式（空きマス数の1次式）のまま延ばしても、速くならなかった。
   - 時間の大半は、MPC を使わない最終段にかかっている。
2. **時間の75〜88%は、MPC を使わない最終段の完全読みである。**
   - 問題57では、最終段のノード数が Edax の1.6倍、1秒あたりのノード数が0.7倍だった。
3. **Deft のノード数は、空きが多いほど Egaroucid より多くなる。**
   - 空き20〜26では、Egaroucid と同じかそれより少ない。
   - 空き28では1.15倍、空き30では1.6〜1.7倍になる。
4. **手順付けを深くすると、少し速くなる。**
   - 空き20以上のゼロ窓の完全読みで、子局面から1手読んだ値で手を並べるようにした（Egaroucid と同じ深さ）。
   - FFO 40〜59 は 3.6% 速くなった。この変更はエンジンに入れた。
   - 57 は変わらなかった。
5. **呼び出しの抜き取りでは、時間の大半（約75%）が空き13以下の探索だった。**
   - 1ノードあたりの処理に、特別に重い所は見つからなかった。
   - 空き14〜30での手の選び方が弱く、末端近くの局面を多く読んでいると考える。

## 1. 空き25以上の傾き・切片

完全読みの規則では、空き25以上の a・b を、空き24の値で止めている（データがないため）。これを式のまま延ばした規則を作り（`make_rules.py` を `E_MEASURED=99` で実行）、FFO 40〜59 を解いた。

| 規則 | 合計 |
|---|---|
| 空き24で止める（今） | 300.6 s |
| 式のまま延ばす | 306.0 s |

- 差の大半は問題55（139.8 → 145.1 s）である。
- 延ばしても、a・b の差は小さい。偶数の深さ8では、切片は空き24で +0.59、空き30で +0.76、空き34で +0.88 になる。

## 2. 段ごとの時間

`trace` で段ごとの時間を測った（`2026-11-01-mpc-tails/tools` を、ワークスペースと同じ LTO 設定でビルドした）。

| 問題 | 空き | 準備（MPC あり） | 最終段（MPC なし） | 最終段の割合 |
|---|---|---|---|---|
| 53 | 28 | 7.4 s | 22.9 s | 75% |
| 54 | 28 | 4.4 s | 33.5 s | 88% |
| 57 | 30 | 6.6 s | 27.1 s | 80% |
| 58 | 30 | 2.8 s | 19.3 s | 87% |

問題57の Edax 4.5.5（`-vv` の出力）との比較：

| | 準備のノード数 | 最終段のノード数 | 最終段の 1秒あたりのノード数 |
|---|---|---|---|
| Deft | 0.30G（85・95・98・99%） | 1.30G | 4,800万 |
| Edax 4.5.5 | 0.39G（73・87・95・98・99%） | 0.82G | 6,900万 |

- 準備を全部なくしても（校正のないモデルで解く）、Deft の最終段は 1.45G ノードだった。
- 準備は、最終段のノード数を1割しか減らしていない。準備の出来は、57 が遅い主な原因ではない。

## 3. 空きマス数ごとのノード数（Egaroucid 7.8.1 との比）

[FFO 40〜59 の比較](../2026-11-03-ffo-engines/README.md)の値から計算した。

| 問題 | 空き | Deft / Egaroucid |
|---|---|---|
| 40〜49 | 20〜26 | 0.52〜1.72（合計 0.75） |
| 53・54 | 28 | 1.16・1.14 |
| 57・58 | 30 | 1.62・1.66 |

## 4. 手順付けの深さ

Egaroucid 7.8.1 は、終盤のゼロ窓探索の手順付けを、残りの深さ / 16 の深さで行う。空き16〜31では、子局面から1手読んだ値（`nega_alpha_eval1`）になる。Deft は、空き24以上でも子局面の評価値だけで並べていた。

子局面から1手読む範囲を変えて、FFO 40〜59 を解いた（診断用の切り替えで試した）。

| 1手読む範囲 | 合計 | ノード数 |
|---|---|---|
| なし | 300.6 s | 15.5G |
| 空き28以上 | 301.4 s | 15.5G |
| 空き24以上 | 296.1 s | 15.0G |
| **空き20以上** | **289.8 s** | **14.2G** |
| 空き16以上 | 308.5 s | 14.3G |

- 空き20以上を採用した。採用した形のエンジンで測り直しても、289.9 s だった（答えはすべて正解）。
- 問題ごとの変化：
  - 速くなった：53（24.1 → 21.8 s）、55（139.8 → 133.3 s）、58（25.2 → 22.9 s）
  - 遅くなった：50（10.8 → 12.1 s）
  - 57 は 31 s のままだった。
- end120（空き20・22・24の120局面）では、合計 150.9 → 150.6 s、幾何平均の比 1.016 で、ほぼ変わらなかった。

## 5. 呼び出しの抜き取り

この機械には perf がない。そこで、問題57の最終段の途中で、gdb で呼び出しを120回抜き取った（`stack_samples.sh`、結果は [stack-samples-ffo57.txt](stack-samples-ffo57.txt)）。

| 部分 | 抜き取りのうちの割合（およそ） |
|---|---|
| 空き13以下の探索（空き6以下の専用処理を含む） | 約75% |
| そのうち空き6以下の専用処理 | 約60% |
| 手順付けのための評価 | 約9% |
| 置換表 | 約8% |
| 安定石による枝刈り | 約5% |

最終段の窓は、空き30では前の段の値 ±2 である。完全読みの値は偶数なので、これは実質1つの値を確かめるだけの一番狭い窓で、原因ではない。

## 残っていること

- 空き14〜30での手順付けの中身。Egaroucid は、隅を重く数える着手可能数や、潜在的な着手可能数も使う。
- どの深さで Edax・Egaroucid より多く読んでいるかは、まだ確かめていない。空きマス数ごとのノード数を数える診断が要る。
- 1秒あたりのノード数の差。正確に測るには perf が要る。
