2026-10-28 マルチスレッド完全読みの計測とEdax・Egaroucidとの比較

対象は `refactor/engine-layout` の `527c906`（deftの実行ファイルSHA-256 `b058df75…f8b6`）。Edax・Egaroucid（AVX-512版）は[前回](../2026-10-28-edax-gap/README.md)と同じビルド。評価データ・MPC（deftは `--legacy-main-mpc`）、主TT約839万項目、FFO40〜49、各局面新プロセス・空TTも前回と同じ。全540実行で公開正解のスコアと空き数までの非選択的な完全読みを確認した。

## 条件

- Intel Xeon 2.80GHz、KVM、4 vCPU（SMTなし）。CPU割当は1スレッド＝CPU 3、2スレッド＝CPU 2〜3、4スレッド＝CPU 0〜3。4スレッドでは測定スクリプト自身も同じCPUを使う（待機中のみ）。
- deft：`exact N 256`（Nは呼出し元を含むスレッド数）。Edax：`-n N`。Egaroucid：`-t N`。
- 6周。周ごとにスレッド数の順を反転し、局面ごとにエンジンの順を回転した（`compare_threads.py`）。各エンジンが報告する探索時間を使う。
- 前回と同じく、再起動後のこの環境は周ごとの変動が大きい（±5%程度）。

| Edax | 27.011秒 | 14.017秒（1.93倍） | 8.584秒（3.15倍） |
| Egaroucid AVX-512 | 29.828秒 | 18.161秒（1.64倍） | 10.435秒（2.86倍） |

| スレッド | 対Edax | 対Egaroucid AVX-512 |

1スレッドではEdaxよりわずかに速いが、スレッド数を増やすと差がなくなる。Egaroucidには全スレッド数で速い。

## ソースから見た改善候補

計測とソースの確認から、次の点を候補とする（未実施。各候補を単独で実装・比較する）。

1. **ヘルパー仕事ごとに局所TTを空から作り直す**：`ybwc.rs` の各ヘルパー仕事は `Context::new` で新しい `EndgameCache` を作る。7〜13空きの層を使うたびに1層24 KiBを確保・初期化し、仕事が終わると捨てる。FFO49の4スレッドでは約4600回の仕事があり、ヘルパーは毎回、局所TTの蓄積なしで探索を始める。ワーカースレッドごとに局所TTを保持して再利用すれば、確保・初期化の費用と、局所TTの命中率低下（並列時のノード増・1ノード費用増の候補）を同時に減らせる可能性がある。再利用には、主スレッドのキャッシュと同じ無効化条件（`clear_tt`、モデル・MPC変更）を適用する必要がある。
2. **仕事ごとの固定費**：仕事は `Box` のクロージャで、`Context` 生成・破棄のたびに統計をMutexで合算する。分割ごとに候補の `Vec` を確保する。
3. **合流時の待機**：子孫の仕事がないマスターは5 msのタイムアウト付き条件変数で待つ。完了通知は `wake` で送られるが、取りこぼし時の待ち時間の上限になる。
4. **分割の粒度**：完全読みのゼロ窓では局所終盤（13空き以下）で分割しないため、分割は14空き以上だけ。Edaxも15空き以上でのみ分割する。小さい局面ではノード増加が大きく、分割位置・最小残り手数の調整が候補になる。

ファイル：`compare_threads.py`（測定スクリプト）、`cpu_use.sh`（CPU時間）、`run/results.tsv`・`summary.json`・`process-output.jsonl.gz`（生データと全出力）。
