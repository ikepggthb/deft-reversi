2026-10-29 マルチコア完全読みの遅い原因の特定と改善

[このPCの基準値](../2026-10-29-local-baseline/README.md)（`3b4e83d`）では、deftは1〜4スレッドでEdax 4.5.5・Egaroucid 7.8.1より速いが、8スレッドでEdax 4.5.5に1.016倍、Egaroucid 7.8.1（clang++）に1.166倍遅かった。8スレッドで遅くなる原因を、他エンジンとの比較と計測で特定し、改善を個別に試した。採用は `9397542`・`01cf50e`・`c0ed2aa` の3コミット。

## 測定条件

- Intel Core Ultra 7 265K（Pコア＝CPU 0〜7、Eコア＝CPU 8〜19、SMTなし、AVX-512なし）。CPU割当は1スレッド＝CPU 4、2＝4〜5、4＝4〜7、8＝0〜7、16＝0〜15、20＝0〜19。環境の詳細は [基準値の記録](../2026-10-29-local-baseline/environment.json)。
- deft：Rust 1.99.1、`RUSTFLAGS="-C target-cpu=native" cargo build --locked --release --example solve`、`exact N 256 --legacy-main-mpc`、モデルSHA-256 `3a07488c…a6069`。主TT約839万項目（他エンジンと同じ）。
- 比較相手：Edax 4.5.5 配布バイナリ（`lEdax-x86-64-v3`）、Egaroucid for Console 7.8.1 配布ソースの公式手順clang++ビルド（readlink修正のみ）。いずれも[基準値の記録](../2026-10-29-local-baseline/README.md)と同じ。
- 局面FFO40〜49。各局面を新しいプロセス・空のTTで解き、全実行でスコアを公開正解（`tools/bench/positions/ffo40-49-answers.obf`）と、空き数までの完全読みの完了を照合した（不一致なし）。
- 版どうしの比較は `compare_many_threads.py`（局面ごと・周ごとに実行順を回転）。時間比は同じ周の基準版に対する10局面合計の比の中央値、「速い周」は基準版より短かった周の数。このPCの周ごとの変動は1〜4スレッドで±0.5%以内、8スレッド以上で±1〜2%なので、4〜10周で判断した。
- 測定中はビルド・テストを並行で走らせていない。

## 1. 原因の特定

### 8スレッドの損失は「ノード増加」と「1ノードの費用増」

`cpu_use.py`（プロセスのCPU時間からモデル読込分を引いたもの、`runs-cpu-use-t8.tsv`）と `perf_counters.sh`（`runs-perf-base.tsv`・`runs-perf-head.tsv`）で、1スレッドと8スレッドを比べた。

| `3b4e83d`、FFO49 | 1スレッド | 8スレッド |
|---|---:|---:|
| ノード | 203.7M | 224.5M（+10%） |
| 命令/ノード | 303.7 | 306.9（+1%） |
| サイクル/ノード | 93.5 | 100.0（+7%） |
| 周波数 | 5.31 GHz | 5.01 GHz |
| L2ロードミス | 1.70M | 7.18M |

- スレッドの稼働率（探索中のCPU時間÷(探索時間×8)）は、大きい局面でdeft 0.89〜0.92、Edax 0.87、Egaroucid 0.78〜0.88で、遊び時間はEdaxと同等以下だった。
- 周波数の低下（約−5.6%）はEdaxでも同じだった。Edaxのサイクル/ノードは1→8スレッドで62.2→62.3と変わらないのに、deftは7%増えた。
- deftの10局面合計のノード増加は8スレッドで+15%（Edax +7%）。

### 1ノードの費用増の原因：偽共有、ジョブごとの局所TT作り直し、コア間移動

`perf record -e mem_load_retired.l2_miss` で8スレッドのL2ミスの場所を調べた。1スレッドではほぼ主TT参照と評価関数だけだが、8スレッドでは局所終盤の入口・一般節点・分割ループの次の読込でミスしていた。

- `Arc<AtomicBool>` の中身（オフセット0x10）や `Runtime` のフィールドの読込。分割のたびに `ancestors`・`cuts`・`Arc<Runtime>` をcloneして参照カウンタを書き換え、ジョブごとに `pending` とstatisticsのMutexを書くので、同じキャッシュラインにある中断フラグ・空き状態フラグ・TTやモデルへのポインタ・`quality` を毎回他コアに無効化されていた（偽共有）。
- 局所終盤TT（13空き以下、スレッドごと1024スロット×8層、約192 KiB）の読込。ヘルパーのジョブは毎回新しい局所TTを確保・初期化して捨てていた。合流待ちの間に子孫のジョブを手伝う場合も、ジョブごとに新しく作っていた。
- コア間移動：探索中の約0.6秒にdeftのスレッドは約2840回コアを移り、Edaxは約730回だった（自発的な文脈切替の回数はほぼ同じ）。移るたびに局所TTなどをL2に読み直す。外部からスレッドをCPUに固定すると、L2ミスが6.0M→4.0Mに減った。

他コアのキャッシュからの転送（`xsnp_no_fwd`）やメモリ順序違反による命令の取り消しは、サイクル全体の0.3〜0.4%で、直接の損失は小さかった。

### ノード増加の内訳

診断パッチ（`diag/apply_diag.py`、コミットしない）で反復ごと・空き数ごとのノードと、βカットで捨てられた兄弟の探索量（以下「無駄」）を数えた（`diag/analyze.py`・`diag/by_empties.py`、生データ `diag/base` など）。`3b4e83d`、1スレッドと8スレッド3回の中央値の比較：

| 段階 | 8/1スレッド | 8スレッドでの無駄の割合 | 増加分に占める割合 |
|---|---:|---:|---:|
| 準備反復（評価探索） | 1.165 | 7.0% | 1% |
| 選択的な完全読み（準備段階） | 1.258 | 21.4% | 17% |
| 完全読み | 1.137 | 5.2% | 82% |

- 完全読みの反復では、13空き以上の一般節点の増加は+2〜6%だが、局所終盤の中の節点は+13.7%増えた。局所終盤の入口1回あたりの部分木が大きくなっている（13空き1.059倍→6空き1.131倍と、下の層ほど増える）。局所TTによるカット率は1%未満（13空きのみ5.9%→4.6%）で、局所TTは主に最善手による手順付けに効いている。
- 1スレッドのまま13空きに入るたびに局所TTを空にすると、ノードは+24.7%増えた（`diag/cold1`）。局所TTには、直前に探索した兄弟・いとこの部分木の情報（合流と最善手）が強く効いている。
- 分割後にβカットになった節点では、カットした手は分割で配った最初の手が約5割、2番目が約3割だった（FFO49）。

Edax（v4.6のソースで確認、4.5.5も同じ設計）は分割した節点に最大3ヘルパー、15空き以上で分割し、8〜14空きは全スレッド共有の主TTを使う。Egaroucidは子が16空き以上のときだけ分割し、6〜12空きはスレッドごとの局所TT（1024スロット）、13空き以上は共有TT。deftは14空き以上で分割し（ゼロ窓の場合）、13空き以下はスレッドごとの局所TT。

各試作の差分は `trials/`、生データは `runs/`。基準は表の「基準」列（`base`＝`3b4e83d`、`padts`＝pad＋tcache＋spin、`01cf50e`・`c0ed2aa`＝コミット）。

- 窓の広い節点やルートでの分割を止める実験（`x-nopvsplit`・`x-norootsplit`）は原因の切り分け用で、どちらも大幅に遅かった（1.288・1.083）。

## 3. 採用した変更

- `9397542` 頻繁に書く共有値と、毎ノード読む値・中断フラグを別のキャッシュラインに分ける。
- `01cf50e` 局所終盤TTをスレッドごとに1つにし、ヘルパーのジョブと合流待ち中に手伝うジョブで使い回す。無効化は従来 `end_cache.clear()` を呼んでいた全ての箇所（TT・モデル・MPC・sigmaの変更）で世代番号を更新する。
- `c0ed2aa` 分割点に、残りの手の数−1まで空きスレッドを集める。

正解・パス・PV・選択率によるTT分離・中断処理・全ワーカー共有の厳密なノード上限は変えていない。局所TTの項目は従来どおり選択率のタグ付きで、ワーカーが保持する局所TTの無効化条件はメインスレッドの局所TTと同じ。

検証（各コミット）：`RUSTFLAGS="-Ctarget-cpu=native" cargo test -p deft_reversi_engine --release -- --include-ignored --test-threads=1`（67件、並列ストレスを含む）、debugのテスト、Clippy（native・通常ターゲット、`--all-targets --all-features -D warnings`）、rustfmt。追加テスト：スレッドの局所TTが同じ世代でのみ再利用され、取り出している間は他のジョブに空の表が渡ること。

## 5. 残る差と次の候補

- 8スレッドでのEgaroucidとの差は、FFO46・47・41・42・44（1スレッドでもEgaroucidが1.4〜1.8倍速い局面。1スレッドの探索木の大きさの差）と、FFO49（Egaroucidは8スレッドで1スレッドの8.3倍速くなり、ノードも減る）に集中する。前者は1スレッドの手順付けの課題（前回までの記録の、7〜12空きの節点がEdaxの1.2〜1.3倍という問題）。
- ノード増加：8スレッド+13%、20スレッド+31%で、Edax（+6%、+15%）の約2倍。局所TTがスレッドに分かれていること（共有すると8スレッド固有で1〜1.5%）や、分割後のカットによる無駄（完全読みで約5〜6%）だけでは説明しきれない。特に準備段階の選択的な完全読みは8スレッドで+26〜30%（無駄が約20%）と効率が悪い。
- コア間移動による費用：スレッドのCPU固定（8スレッド−1.9%）は依存の追加が必要。待機前のスピンは2〜4スレッドで遅くなった。待機の仕方（スピンの長さ、ワーカーと合流待ちで別の扱い）を変えて再試行する余地がある。
- L3に収まる小さな共有表で12〜13空きの結果を共有する案（主TTより費用が小さい）。
