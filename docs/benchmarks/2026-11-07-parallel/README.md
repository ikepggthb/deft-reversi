# 多スレッドの完全読み：分割の下限をスレッド数と段階で変える（2026-11-07）

[FFO 40〜59 の比較](../2026-11-07-ffo-engines/README.md)で、20スレッドでは Egaroucid 7.8.1（20.1 s）が Deft（20.6 s）より速かった。原因を調べ、終盤の分割の下限をスレッド数で変えるようにした。

## 結果

最終版（下の「2. 準備の段階」まで入れたもの）。FFO 40〜59 の合計（中央値）、基準は `0f11ef5`、モデルは `mpc-pen-1000/model.dpr2`（[queue2.sh](queue2.sh)、[queue2.log](queue2.log)）。

| スレッド（CPU） | 前 | 1 だけ | 最終 | 最終／前 |
|---|---|---|---|---|
| 20（0〜19） | 20.69 s | 18.47 s | **17.97 s** | **0.869**（5/5 回速い） |
| 12（0〜11） | 25.29 s | 23.90 s | **23.55 s** | **0.931**（3/3） |
| 8（0〜7） | 29.81 s | 29.43 s | 29.42 s | 0.987 |

8スレッド未満は前と同じ設定。1スレッドは並列探索を使わないので変わらない。

## 1. 最後の完全読みの分割の下限をスレッド数で変える

FFO 40〜59 の合計（中央値）。

| スレッド（CPU） | 前 | 後 | 比 | 後が速かった回 | ノード数 |
|---|---|---|---|---|---|
| 20（0〜19） | 20.48 s | **18.54 s** | **0.896** | 5/5 | 136.5億 → 132.6億 |
| 12（0〜11） | 25.11 s | **23.73 s** | **0.944** | 3/3 | 130.0億 → 127.1億 |
| 8（0〜7） | 29.83 s | 29.56 s | 0.992 | 3/3 | 125.8億 → 125.4億 |
| 4（4〜7） | 55.73 s | 55.81 s | 1.002 | 1/3 | 同じ設定（差は揺れ） |

20スレッドの 18.5 s は、[同じ日に測った](../2026-11-07-ffo-engines/README.md) Egaroucid（20.1 s）・Edax（24.5 s）より速い（別の回に測った値どうしの比較）。1スレッドは変わらない（並列探索を使わない）。

## 原因

| | 終盤（完全読み）で分割する下限 | 中盤で分割する下限 |
|---|---|---|
| Deft（前） | 空き10（局所終盤の13以下は分割しないので、根以外は実質14） | 残り深さ4 |
| Egaroucid 7.8.1（`ybwc.hpp`） | 子の深さ16以上（親が空き17以上） | 子の深さ6以上 |

1スレッドあたりの処理速度（ノード/秒）は、20スレッドでも Deft と Egaroucid で同じ程度だった（1スレッドに対して Deft 0.58倍、Egaroucid 0.55倍）。差は分割の細かさにあった。

FFO 54（空き28）を20スレッドで解いたとき：

| 下限 | 分割 | ヘルパーの仕事 | 合流の待ち（全スレッド） | ノード | 時間 |
|---|---|---|---|---|---|
| 14（前） | 286,430 | 470,694 | 11.3 s | 2,096M | 2.71 s |
| 17 | 22,169 | 66,881 | 6.9 s | 2,093M | 2.40 s |

スレッドが多いと、ほぼいつも暇なスレッドがいるので、空き14〜16の小さな節点でも次々に分割する。ノード数はほとんど変わらず、仕事の受け渡しと、分割した側が最後のヘルパーを待つ時間が増えていた。

暇なワーカーが眠る前に最大50・500 µs 回って仕事を待つ試作も作ったが、FFO 54 で変わらなかった（2.71 → 2.75 s、2.31 → 2.29〜2.47 s）。起こす遅れではなく、合流の待ちが損失である。

## 下限を変えた試し

[tune.py](tune.py)（Deft だけ、1問ごとに新しいプロセス、設定の順番を問題と回ごとに回す）。前の値（14）に対する時間の比：

| スレッド | 15 | 16 | 17 | 18 | 20 |
|---|---|---|---|---|---|
| 20 | 0.94 | **0.89** | **0.89** | **0.89** | 0.97 |
| 12 | | 0.95 | 0.95 | | |
| 8 | | | 1.00 | | |
| 4 | 1.00 | 1.01 | 1.01 | | |

- 中盤の下限を6・8 にしても、20スレッドで ±1% 以内（`runs/a.tsv`、`runs/b.tsv`）。変えなかった。
- 4スレッドでは下限を上げると少し遅くなる。暇なスレッドが少なく、分割の機会を減らすと遊ぶ時間が増えるためと考えられる（推測）。

## 2. 準備の段階は元の下限に戻す（1 のあとの調査）

20スレッドで、1スレッドより読む局面が多い（122億 → 133億、+9%）理由を調べた。一時的な計測コード（コミットしない）で、1つの完全読みを段階ごとに分けて数えた（FFO 40〜59 の合計、1 を入れた版）。

| 段階 | ノード（1 → 20スレッド） | 20スレッドでの速さの倍率 | 20スレッドの時間 |
|---|---|---|---|
| 中盤の準備（深さ） | 11M → 17M（1.50倍） | 1.4倍 | 0.62 s |
| 確率85% | 321M → 456M（1.42倍） | 4.4倍 | 1.62 s |
| 確率95〜99% | 461M → 501M | 5〜9倍 | 1.20 s |
| 最後の完全読み | 11,401M → 12,210M（1.07倍） | 12.8倍 | 15.21 s |

- **準備の段階は並列で速くならない。** 確率85% の段階だけを解かせると、20コアのうち平均6〜7コアしか動いていなかった（CPU時間／経過時間）。ProbCut で枝が細く、分割の下限17 では分ける所がさらに少ない。
- **最後の完全読みの +7% は、空き6〜27 のどの空き数でも一様に 5〜12% 増えている。** 末端の局所 TT（1スレッドに1つ、空きごとに1,024項目）で増えているのではなく、分割する上の節点で増えた分がそのまま下に広がっている。
- 増えた分のうち、カットで途中で打ち切られた兄弟の探索は19〜46%（入れ子の分割を二重に数えないようにした）。カットした手より後ろの手を読み終えていた分は1%未満。最後の完全読みは null window の探索だけで、窓を広げた読み直しは0回だった。残りは読む順番が変わって TT の中身がずれる間接の影響と考えられる（推測）。同じ問題を20スレッドで何度か解くと、ノード数は ±3% 揺れる。
- TT を 256 MiB から 2 GiB にしてもノード数は変わらなかった。
- **Egaroucid の +1% は、問題ごとには 0.58〜1.66倍とばらつく。** 一番重い問題55 が 0.95倍、49・51 が 0.69・0.58倍で、合計が小さく見える。55 を除くと Egaroucid +7%、Deft +13%。

試したこと（20スレッド、`runs/sel.tsv`、`runs/elder.tsv`、4回）：

| 試したこと | 時間 | ノード | 判断 |
|---|---|---|---|
| 準備の段階（確率つき）だけ分割の下限を14 に戻す | **0.978**（4/4） | +1% | **採用** |
| 同じく15 | 0.988（3/4） | | |
| ProbCut の浅い探索（深さ8以上）でも分割する | 0.990（2/4） | | 見送り |
| 上の2つを両方 | 0.976（4/4） | | 14 だけと差がない |
| 分割の前に兄弟をもう1手、1スレッドで読む | **1.248** | **−3.5%** | 不採用 |

最後の行のとおり、余分なノードを減らすと並列にできる仕事も減って遅くなる。ノードの増加は並列化の代償で、Egaroucid と同じ +1% を目標にしても速くはならないと考える。

## 変更

- `tree::split_empties(threads)`：最後の完全読みの下限。8スレッド未満は前と同じ `SPLIT_EMPTIES`（10、根以外は実質14）、8以上は `13 + min(threads, 16) / 4`（8〜11 で15、12〜15 で16、16以上で17）。`Runtime::split_empties` に持たせる。
- `Context::exact_split_empties()`：確率つきの段階（`sigma` がある間）は `SPLIT_EMPTIES`、最後の完全読みは `Runtime::split_empties`。`search_siblings` と根の分割で使う。

テスト `ybwc_exact_repetition_and_thread_counts` は、8・20スレッドでは空き10の局面で分割しなくなったので、空き20の局面（答えは1スレッドの探索）で分割と答えを確かめる部分を足した。
