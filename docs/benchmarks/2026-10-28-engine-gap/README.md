2026-10-28 Edax・Egaroucidとの1コア終盤差の調査と改善

対象は `refactor/engine-layout` の `ab92aea`（以下「変更前」）から、このディレクトリと同時にコミットした `2672cd7`（以下「最終」）まで。比較相手はEdax 786421f355219ade872ce7285c1cab1eaf67836a、Egaroucid 2a65c87860be999373088ad833aa00b0844883b6（過去の3エンジン比較と同じコミット）。

過去のレポートは当時の記録として扱い、以下の数値はすべて今回の環境で取り直した。過去のAMD EPYC環境の絶対時間とは直接比べない。

## 測定条件

- Intel Xeon 2.80GHz（KVM、4 vCPU、L2 4 MiB/コア相当の表示、L3 33 MiB）。測定はCPU 2固定、ビルドはCPU 0。測定中はビルド・テストを並行実行していない（プロファイル取得もしていない）。
- 1スレッド、時間・ノード上限なし。各局面を新しいプロセス・空のTTで解く。モデル読込・TT確保は計時外。
- 局面はFFO40〜49（`tools/bench/positions/ffo40-49.obf`）。全実行で公開正解（`ffo40-49-answers.obf`）・完全読みの深さ（空き数）・`Exact`/`Completed` を照合した。照合に失敗した実行は1件もない。
- deft：Rust 1.99.1（`rust-toolchain.toml`）、release、fat LTO、`-C target-cpu=native`、既定feature、主TT 256 MiB＋PV 16 MiB、`exact`、`--legacy-main-mpc`。
- Edax：GCC 13.3、`make build CC=gcc ARCH=native`（`-Ofast -flto -march=native`）、`-l 60 -h 23 -n 1 -book-usage off`。
- Egaroucid：G++ 13.3、`-O3 -flto -march=native`（SIMD版）と `-DHAS_AVX512` 追加（AVX-512版）。今回のCPUはIntelなので `-DHAS_AMD_PROCESSOR` は付けない（過去のAMD環境のビルドとは異なる）。`-t 1 -l 60 -nobook -hash 23`。
- 主TTの項目数は全エンジン約839万。項目サイズ・付随表は異なり、総メモリ量は同じではない（過去の記録と同じ注意）。
- 過去記録のコンパイラはGCC 14.2だった。今回の環境にはGCC 13.3しかないため、Edax・Egaroucidの絶対時間は過去と比べない。

### 評価データ・MPC

`eval-v4.bin` はリポジトリに存在しないので使っていない。deftのモデルはリポジトリの旧main評価から次の手順で作った。

```sh
python3 tools/convert_legacy_eval.py data/eval/eval.json /work/eval-legacy.json
python3 tools/convert_pattern_v2.py /work/eval-legacy.json /work/deft-eval-main.dpr2
```

生成物のSHA-256は `3a07488cc364975eed03fe01c1806a6ff2737e99f5879f70f21dc023d64a6069` で、過去の測定に使われたモデルと一致した。旧mainの評価JSONにはMPC係数が入っていないため、全実行で `--legacy-main-mpc`（`Engine::set_legacy_main_mpc`）により旧mainの終盤MPC表を明示した。完全読みの最終段階はMPCを使わない。準備探索の選択率段階は既定のまま。

Edaxの評価は公式リリースv4.4の `eval.7z` を展開した `data/eval.dat`（SHA-256 `f8b2299612d9fa4414157e70e932636e33111c2602d0c2fc382a7d90ef21b792`、過去記録と一致）。Egaroucidは付属の `eval.egev2`・`eval_move_ordering_end.egev`（過去記録とハッシュ一致）。Egaroucidの `hash23.eghs` は `tools/bench/make_egar_hash.cpp` で固定シードから再生成し、過去記録と同じSHA-256 `0a44b764…d323` を確認した。

### Egaroucidのコンソール側の修正

最初のベースライン測定中、Egaroucid SIMD版が1回だけ評価ファイルを開けずに終了した。`src/console/console_common.hpp` の `get_binary_path()` が `readlink` の結果を終端しないため、未初期化のスタック内容次第で実行ファイルのディレクトリを誤る。探索とは無関係なこの1行だけを修正し（`egaroucid-console-readlink.patch`）、両ビルドを作り直した。途中で止まったその測定は結果に使っていない。

## 2. 原因の特定

ノード数と1ノードの費用を分けるため、両エンジンに空き数別の訪問節点数を数える診断用パッチを当てた（`node-histogram/`。コミットしたエンジンには含めない）。Egaroucidは既存の `USE_SEARCH_STATISTICS` を有効にし、反復ごとに出力させた。deftは各カーネルの入口で数え、13空きの二重計上を除いた。数え方は両者で「その空き数の節点を1回訪問したら1」にそろえたが、14空き以上ではEgaroucidが手順付け用の浅い探索の節点も同じ配列に数えるため比較に使わない。

変更前の最終反復（完全読み）、10局面合計：

| 空き | deft | Egaroucid | 比 |
|---:|---:|---:|---:|
| 4 | 88.1M | 67.9M | 1.30 |
| 5 | 65.5M | 57.6M | 1.14 |
| 6 | 34.9M | 36.1M | 0.97 |
| 7〜10 | 64.3M | 75.9M | 0.85 |
| 11〜13 | 7.2M* | 9.6M | 0.75 |

（*13空きは二重計上を除いた値。生データは `node-histogram/raw-base/`、集計は `base-vs-egaroucid.txt`。このときの診断パッチは13空きを一般節点と局所終盤の入口で二重に数えるため、表では局所終盤側だけを数えた値1.20Mを使った）

7空き以上ではdeftの方が節点が少なく、手順付けは劣っていない。差は5→4、6→5の展開数で、deftは6空き1節点あたり1.88個の5空き子を訪ねるのに対しEgaroucidは1.59個だった。EgaroucidとEdaxは5〜6空きで安定石カットを行い、Egaroucidは5〜6空き（と4空き）で「8近傍に他の空きがない升」を先に探索する。deftは四分割parityのみで安定石カットもなかった。

cpu-clockのサンプリング（`perf record -e cpu-clock`、ハードウェアカウンタはこのVMで使用不可）では、変更前の時間は7〜13空きの入口（`endgame_score_entered`、6〜13空きと手順付けをインライン化した関数）34%、2〜4空きカーネル31%、安定石判定9%、パターン評価と状態更新8%、主TT参照4%。7〜13空きの入口の約2割は、子局面の局所TT照会で不一致だった場合の分岐先1命令に集中していた（後述の試作から、分岐予測ミスと読込待ちの両方を含むと判断）。

小さい局面（FFO40・44など）では、辺安定テーブル（65536項目）の初回計算が探索の計時内に入っていた。この環境で1プロセスあたり約0.07〜0.09秒で、FFO40の探索時間の2割を超える。

## 3. 試作と採否

すべて `compare_many.py`（このディレクトリ）で比較した。各局面を新プロセスで解き、局面ごと・周ごとに実行順を回転し、版の数の倍数の周回で全順位を均等にする。「時間比」は同じ周の基準版に対する10局面合計時間の比の中央値、「速い周」は基準版より短かった周の数。ノード数は `SearchStats::nodes`（決定的で、全周同一だった）。各試作の差分は `trials/`、生データは `runs/` にある。

## 6. 残る差と次の候補

- 11〜13空きの順序付け専用の小さいパターン表（学習が必要）。上記のとおり評価値順序の効果自体は確認済み。
- 升種別順の差分更新実装（Edaxの空き升リスト）。ノードは最大17%減ったが、今回の実装では費用が上回った。
- 2〜4空きカーネル（全体の約27%）。Egaroucid（Edax AVX由来）は最後の1マスで「着手可能か」だけを調べる遅延カットなどSIMD化を進めている。
- 1合法手の局所TT処理、14空き以上のNWSのPV配列は、今回の分布では費用が小さく未着手。
