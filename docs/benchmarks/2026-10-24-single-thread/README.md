# 単一スレッド性能の調査と改善

> 訂正: 旧版比較は低水準APIを使用しており、通常の探索制御を含まない。通常API `solve(board, 60)` で再測定すると旧版1.801秒・新版5.284秒で、新版は約2.93倍の時間を要した。「旧版より高速」という通常利用時の結論は撤回する。[再測定結果](../2026-10-24-public-solve/README.md)。

## 結果

同じPコア、同じモデル、同じFFO 40–44、メインTT 256 MiB、MPCなし、native releaseで比較した。
改善前後を同じ測定内で交互に5回実行し、各局面は新しいプロセスで解いた。モデル読込と初期化は探索時間から除外。

- 合計中央値: **9.205324秒 → 5.282299秒**。
- 改善前比: **1.743倍**、時間は **42.6%短縮**。
- 全局面のスコアが一致。深さや選択率を弱めた短縮ではない。

| 対象 | 改善前 | 改善後 | 倍率 |
|---|---:|---:|---:|
| FFO 40 | 0.453269秒 | 0.278704秒 | 1.626倍 |
| FFO 41 | 1.300675秒 | 0.660522秒 | 1.969倍 |
| FFO 42 | 1.080873秒 | 0.673308秒 | 1.605倍 |
| FFO 43 | 4.917860秒 | 2.726699秒 | 1.804倍 |
| FFO 44 | 1.452224秒 | 0.941024秒 | 1.543倍 |

## 原因の調査

FFO 43をユーザー空間の命令ポインタサンプリングで調べた。
`perf` はOS権限で拒否されたため、システム設定は変更せず `ITIMER_PROF` の1ms周期で取得した。
これは実行ファイル内の自己時間の概算で、ハードウェアのキャッシュミス数や完全なコールスタックを測定したものではない。

- 汎用探索 `Context::node` のサンプル比率は改善前 **44.9%**、改善後 **2.0%**。
- 改善前の最頻命令は256 MiB共有TTのスロットを読み出した直後の判定付近。`tt-load-before.asm.txt` に逆アセンブルを保存した。
- 終盤7–12空きでも、大きな共有TT、汎用候補リスト、評価状態、PV用の戻り値を通っていた。
- この範囲を局所表と値専用経路に移すと、同等以上のノードを読む局面でも処理時間が大きく短縮した。共有表へのランダム参照と汎用経路のコストが主因と判断した。

サンプル比率の分母はシンボルへ対応づけられた実行ファイル内サンプル。ライブラリ内サンプルは別集計。
割合だけで関数の絶対時間が増減したとは判断しない。性能の採否はサンプラーを使わない比較測定で決めた。

## 実装

- 終盤の幅1探索、MPCなし、空き12以下を専用経路へ分離。PVが必要な通常幅探索は既存経路を維持。
- 空き6–12ごとに2048項目の局所TT。完全な盤面を照合し、確定的な完全読みの上下限だけを保存する。
- 各層は必要になった時点で確保。最大7層で約336 KiB。ワーカー間では共有しない。
- 7–12空きの候補は最大12件の小さいリストを使用。子の合法手を手順付けと再帰で再利用。
- 合法手が1つなら並べ替えを省略。相手の石をすべて反転した場合は確定値64で終了。
- 主スレッドの局所表はEngineで保持し、要求中はContextが所有。再探索に再利用する。
- `clear_tt`、モデル変更、MPC設定変更で局所表も無効化。中断した未完了ノードは保存しない。
- MPC使用時には元の探索経路を使い、選択的な境界を局所表へ混在させない。

## 再探索と回帰検証

同じFFO 43を同一Engineで4回解き、4回目を比較する測定も5周実施。
改善前は約0.582ms、改善後は約0.577ms。差は小さく、ウォームキャッシュ時の性能を維持した。

- 通常構成: 39件成功、ストレス1件は別途実行。
- native release: **全40件成功**。通常/native両方のClippyが警告なし。
- 幅1探索の上下限と総当たりの照合を8空きまで拡張。
- 9空きの正解とPVを、初回・再探索・表の消去・モデル変更後で照合するテストを追加。
- 外部停止、ノード上限、パス、並列反復、MPC分離の既存テストも成功。

## 旧エンジンとの再比較

参照先f4192a0の `solve_eval` / `solve_final` と現在の実装を、CPU 1に固定して5周比較。
旧版のSolverとスレッド内TTは毎局面作り直し、新版も表を消去する。

| 対象 | 旧版 | 改善後 | 旧版比 |
|---|---:|---:|---:|
| 中盤24局面・深さ8 | 0.215156秒 | 0.145013秒 | 1.484倍 |
| FFO 1–19・完全読み | 0.216977秒 | 0.040507秒 | 5.357倍 |
| FFO 40–44・完全読み | 8.298906秒 | 5.284832秒 | 1.570倍 |

以前の「重い終盤の単一スレッドが旧版より約11%遅い」という状態は、この測定集合では解消した。
各局面・別のCPU・別のモデルに同じ倍率を保証するものではない。

## 再現手順とデータ

- `tools/bench_rewrite_versions.py`: 改善前後のsolveバイナリを同じコア上で交互に比較。`--repeat-in-process 4` はウォーム測定。
- `tools/engine-compare`: 参照先エンジンとの比較。
- `tools/bench_rewrite_parallel.py`: 並列測定。CPU割当とスコア一致も検証。
- `sampler.c`: 診断用サンプラー。Linux x86_64の単一スレッド専用で、エンジンの一部ではない。
- `tools/summarize_rewrite_profile.py`: `nm` で命令オフセットを関数へ対応づける。

サンプリングの例（通常の速度測定にはサンプラーを読み込まない）:

```sh
gcc -shared -fPIC -O2 -Wall -Wextra -Werror docs/benchmarks/2026-10-24-single-thread/sampler.c -o /tmp/deft_sample.so -ldl
taskset -c 1 env LD_PRELOAD=/tmp/deft_sample.so DEFT_SAMPLE_OUT=/tmp/solve.samples target/release/examples/solve /tmp/deft-pattern.dpr2 /tmp/deft-ffo43.obf exact 1 256
python3 tools/summarize_rewrite_profile.py target/release/examples/solve /tmp/solve.samples /tmp/profile.json
```

改善前のバイナリは作業開始時の実装を `/tmp/deft-single-before` に退避したもの。
`before-after.json` に双方のバイナリハッシュ、モデル・局面ハッシュ、各周の時間を保存した。
`environment.json` にソースのスナップショットハッシュ、Rust、ビルド条件、検証件数を記録。
生データ、プロファイル、並列・再探索測定は同じディレクトリのTSV/JSON。
初回実装の測定は `../2026-10-24/README.md` に履歴として残す。
