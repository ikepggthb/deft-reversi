# Bookの検証

## 保守性を見直した後の確認

比較元は69051e8。評価の階層と重複した表示情報、通常の局面にあった旧途中状態、使わない旧採用方式の保持欄を除いた。[変更理由と残る複雑さ](maintainability.md)を参照。

全workspace・全featureのrelease試験205成功、既存の負荷試験1件は実行対象外。book既定feature＋CLIは109成功。Clippy全target・全feature、警告をエラーにした非公開項目を含むRustdoc生成、整形検査も成功した。HTMLは15ページを生成・リンク検査した。

|確認対象|結果|
|---|---|
|評価の対象範囲|一部の手の最大値や特定の手の評価を、子局面全体の値へ読み替えない。現行Evaluationと旧形式の検査でそれぞれ確認|
|推定と確定|中盤Fullや選択的終盤から最終石差の確定情報を作らない。手動指定とは独立した最終石差の情報を維持|
|編集・登録・解除|小終盤の独立した区間計算と96段階の操作列、矛盾時の復元、子からの反映を継続して確認|
|中断と再開|探索中の途中値は完了扱いにせず、仕事を戻す。旧途中結果は読込中だけで取り込む|
|旧形式|固定v6/v2・v7/v3を読み込める。手動値と旧探索を混ぜたv3の品質は、旧情報の検査後に再集計|
|既存v8/v4|改修前のバイナリで作った固定入力を読み込み、再保存した全バイトが一致|
|実book|26,527局面・289,881候補・26,851登録手を旧形式と既存v8の両方から全件照合。既存v8/v4の実bookも再保存後の全バイトが一致。元ファイルのSHA-256は不変|
|実モデル|v3-pen・18スレッドで、新規生成・保存再開・設定変更・既存bookへの追加・合法な対局手の選択を確認|
|完了する固定探索|6局面・67候補の既知の値・品質・登録が3回とも改修前と一致|
|対局利用|通常の手の選択で問い合わせごとのメモリ確保0回を維持|

## 同じ実bookの費用

同じv8/v4を使い、69051e8から再ビルドした測定用プログラムと現在版を交互に測定。3回の中央値。

|項目|69051e8|今回|
|---|---:|---:|
|生成用データ見積もり MiB|90.9|89.8|
|対局用データ見積もり MiB|8.6|8.6|
|play読込 ms|41.5|44.0|
|work読込 ms|154.7|148.0|
|play保存 ms|17.5|17.8|
|局面参照＋候補の点数走査 ns|33.0|33.3|

生成用の見積もりは局面・評価・仕事一覧などの保持分。Engine・モデル・探索表を含む総使用量ではない。参照速度はmoves()の点数走査であり、詳しい記録の表示や手の選択全体の費用ではない。メモリ見積もりの増加はなく、読込・通常参照に10%を超える悪化はなかった。理解の容易さを、この速度の結果だけで判断しない。

固定6局面・深さ8 Full・18スレッド・TT128MiBの完了探索は、生成処理の中央値0.049秒。新旧で経過時間の短い標本なので、長時間生成の倍率へ一般化しない。

## 再現と限界

機能試験はtestsと各モジュール内。既存形式の入力はtests/fixturesへ固定した。今回の実bookの監査・測定・コマンド・ハッシュは`local/work/book-maintainability-review/RESULTS.md`と同ディレクトリのJSON・ログに保存した。以前の構造変更の測定とは比較元が異なる。[以前の検証記録](https://github.com/ikepggthb/deft-reversi/blob/69051e880cbf5a8dc639d7bc8e3a8a74268bcc72/docs/book-v2/validation.md)も参照できる。

長時間・大規模の生成、棋力、外部入力の申告を再探索して確かめること、スマホ実機の見た目は未検証。今回もEngineの再帰探索・レベル表・探索revisionは変えていない。将来の中盤レベル＝同じ探索元での要求深さへの切替は未実装である。

Rust APIには変更があるため[移行表](compatibility.md)を参照。保存形式を変更したり、旧ファイルの検査を緩めたりした改修ではない。
