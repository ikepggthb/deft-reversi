# 保守性の見直し

`deft_reversi_book` では、「普通の変更をするために理解すべき独自の分類をいくつ減らせるか」を基準にデータ構造と処理を整理している。

## 1. 評価の表現を一つにまとめる

以前は `Assessment`、`ValueClaim`、`ValueAnalysis` から `Derivation`、`CalculationSubject`、`SearchProjection` などをたどって対象と値の意味を調べる構造になっており、簡易表示用の点数・深さ・確定フラグも重複して持っていた。

現在は `Evaluation` 一つが点数・探索条件・出所・モデル識別値を持つ。点数は `result()`、条件は `conditions()`、出所は `source()` で直接読める。子から計算した値を作る場合も「導出→計算→対象」といった入れ子を組み立てず、子の盤面と条件を直接記録する。

点と上下限、中盤と終盤、推定と最終石差、要求条件と完了条件は引き続き区別している。これらはリバーシの評価を正しく扱うために不可欠な情報であり、単一の深さ番号へ潰すことはしていない。

## 2. 旧形式の都合を通常処理から外す

旧評価の分類、計算元のハッシュ、旧採用方式、旧バイナリ表現は `legacy` モジュールへ移し、旧形式の検査で当時の解釈が必要な場合だけ使うようにしている。

現行の `BookEditor`、`Book`、生成処理は旧採用方式を持たず、局面にあった旧方式の途中結果欄も削除した。旧ファイルの完了済み候補は読み込み中に取り込み、現行の局面データへ途中状態を持ち込まない。一時的な保存用の評価一覧も `format.rs` 内に閉じ込め、対局用データを作るだけで保存用の一覧まで理解する必要をなくした。

## 3. 採用規則だけを切り離して読めるようにする

以前は局面の検索・参照番号の解決・値の採用が一つの処理に混ざっていた。現在は、候補を集める処理（`move_values_at`）と採用する値を選ぶ処理（`MoveValues::choose`）を分けている。採用規則をレビューするときは、手動値・最終石差・子の値・直接値・集合探索の比較だけを追えばよい。

診断で返す名前も、`direct`、`child`、`manual`、`final_score`、`selected` など何の値かがすぐ分かる名前にしている。親へ返すための保持欄も「backup」ではなく、親の手番から見た値であることを示す名前にした。

## 4. 多義的な名前を分ける

かつて「Frontier」という名前が「集合探索の記録」「優先順の種類」「未登録手だけを再計算する設定」の 3 つの意味で使われていた。これをそれぞれ `MoveSearch`、`SchedulePolicy::Promising`、`unregistered_only` へ分け、動作が名前から読めるようにした（CLI の `--schedule frontier` は互換性のため引き続き受理する）。

使用許可が二通りしかない旧評価・計算値の設定も、専用の方針型をやめて `allow_imported`・`allow_calculated` という真偽値にし、手動値の `allow_manual` とそろえた。

## 5. それでも残る複雑さ

次の 4 つはドメイン固有の要件であり、単純な点数と深さだけに落とすと既知の情報を失ったり登録範囲を誤ったりするため、意図的に残している。

- 登録した進行が合流（転置）する場合の損失制限（`(距離, 累積損失)` の組の保持）
- 手動値とは独立した最終石差の確定情報の保持
- 中断した仕事の再開状態
- 旧形式ファイルの読み込み検査

また、メモリを節約するための共有配置（`values.rs`）は読取用の `Evaluation` とは形が異なるが、その違いは `values.rs` と `format.rs` の境界へ閉じ込め、通常の編集・生成が旧表現や保存形式へ変換しながら進む構造にはしていない。

今後も機能を追加するときは、型名や行数だけでなく「[ソースの読み方](source-review.md) の操作を、旧形式の内部や内部番号へ寄り道せずに追えるか」を基準にレビューする。
